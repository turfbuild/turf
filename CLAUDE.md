# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```sh
make build      # compile to bin/turf (embeds git-derived version)
make test       # go test ./...
make fmt        # go fmt ./...
make vet        # go vet ./...
make tidy       # go mod tidy
```

Always build with `make build`, not `go build` — the Makefile injects the git-derived version via ldflags, which a bare `go build` omits.

Run a single test:
```sh
go test -run TestName ./...
```

## Architecture

`turf` is a thin CLI wrapper around the `turf-mcp-server` binary. It never imports turf server code — the only contract is MCP over stdio.

**Data flow:**
```
CLI (cobra commands) → createAgentRuntime() → cagent runtime → turf-mcp-server subprocess (MCP/stdio)
                                                             → OpenTofu providers (downloaded on demand)
```

**Key files:**
- `agent.go` — constructs the cagent runtime. Launches `turf-mcp-server` as a subprocess, wires up toolsets (MCP tools, filesystem, think, todo, memory, and — when present — user skills), and creates the cagent `agent`/`team`/`runtime`. Registers the MCP toolset under the **`turf` name** so cagent prefixes every server tool with **`turf_`** (e.g. `turf_skill_core`, `turf_read_skill_file`) — see the Skills note below for why. Contains `workflowInstructions`, a short persona that delegates workflow guidance to the MCP server's instructions and `turf_skill_*` tools, spells out the `turf_` prefix mapping (the server names its own tools bare), distinguishes those from user `read_skill` skills, and carries the **dispatch-ordering note** — batched tool calls execute sequentially in emission order, so the persona tells the model to order dependent calls correctly within a batch and to await a call's *result* before emitting a call whose arguments need it. Sequential execution comes from `runtime.WithSequentialToolCalls(true)` at `runtime.New`, a **cagent fork patch** (upstream ≥ v1.99.0 fans a model batch out in parallel, unconditionally — which raced turf's stateful, order-dependent planning tools into ordering errors; prompt-only discipline proved insufficient). The API-level `parallel_tool_calls=false` knob was rejected: only the OpenAI/DMR providers honor it (Gemini, turf's default, ignores it) and it costs one LLM round-trip per call, while dispatcher-side serialization keeps multi-call batching free. Drop the fork patch when upstream ships its planned tool-execution-strategy config.
- `mcptoolset.go` — `turfMCPToolset`, a thin decorator around the MCP toolset that improves how turf's tools present in the **`/tools` dialog**. `Tools()` files each tool under a functional sub-category (`turf · plan`, `turf · apply`, `turf · provider`, `turf · workspace`, `turf · state`, `turf · skills`) and gives it a friendly, verb-first **display** name (`turf_plan_approve` → "Approve Plan") via `Annotations.Title`, instead of one flat `turf` group of raw `turf_*` ids. Both come from `turfToolInfo`, the per-tool source of truth. Display-only — the model still calls `turf_*`; providers and permissions key on `Name`. The tool set (group + title) is kept in lock-step with the `permissions.go` lists by `mcptoolset_test.go`. `Kind()` masks the inner `MCP` classification so turf reads as a built-in capability, not an external MCP integration. The dialog itself (layout, sorting, **description truncation**) is owned by cagent and not customizable without forking, so these data-side fields (`Category`, `Annotations.Title`) are turf's only lever over it.
- `renderers.go` — custom TUI **timeline** renderers for every `turf_*` tool (one-liner that leads with the friendly `turfToolInfo` title, then target + colored status, with a Ctrl+O expand block: attribute diffs, ready-sets, evaluated outputs). Plugs into cagent's renderer registry through the **same entry point its own built-ins use** — `tui.WithToolRenderers(map[string]tool.Builder)` → `tool.Register`, with `tool.Builder` + `toolcommon.NewBase` + `toolcommon.Renderer` — keyed by exact tool name. The renderer map comes from `turfToolRenderers()`; the full TUI wires it via `tui.WithToolRenderers`, while the lean TUI (which never calls `tui.New`) registers the same map directly through the `registerTurfToolRenderers()` helper — both funnel through `tool.Register`, so lean and full render tools identically. Deliberately hand-writes each `Renderer` (not cagent's `SimpleRenderer`/`RenderTool` helpers, which model a one-arg/one-result line) and parses `msg.Content` JSON (not a typed `msg.ToolResult.Meta`, since turf results cross the MCP boundary as text). The leading title is resolved in `line()` from `turfToolInfo` rather than `DisplayName()`. Every tool has a renderer and every renderer leads with its title — both enforced by `renderers_test.go`. **Failed tool calls surface the framework's error text** rather than a bare title, and **lead with the request's target** so a failure is as scannable as a success: on `ToolStatusError`, cagent carries the error message in `msg.Content` (from its `ToolCallResult.Output`), which the shared `errorLine` renders as a red body (`styles.ToolErrorMessageStyle`) prefixed by the target (`addr(target) + " · "`) resolved via `errorTarget` — a per-tool `turfToolTargetArgs` lookup (mirroring each renderer's own running-branch target arg: `resource_addr`, `path`, `address`, provider `name`, …) with a universal `workspace_alias` fallback, read from `msg.ToolCall.Function.Arguments`. It follows the same Ctrl+O detail toggle as every other line — expanded, the full error wraps across as many lines as it needs; compact, it flattens to one line truncated with an ellipsis (`ansi.Truncate`, measured against the title+target prefix width so the target stays visible) to stay scannable (empty → `"failed"`). It reaches every renderer through the single uniform swallow point, the `!parseContent` fallback (now `fallbackLine`, which defers to `errorLine` on error else the bare title, so the completed-but-unparseable case is unchanged); the two renderers that don't parse JSON (`renderSkill`, `renderReadSkillFile`) call `errorLine` directly, and `TestEveryRendererReportsErrors` guards that none regress to a silent bare line. **Rendering OTF values (the general approach):** every JSON-decoded OpenTofu value funnels through one shared renderer, `renderValue` (+ `renderMap`/`renderList`), so nested maps/lists never fall through to a raw-JSON dump. It renders in the **`tofu plan` idiom** (which is HCL-*like*, not HCL — `=`-aligned `key = value`, `+`/`~`/`-` markers, `(known after apply)`, masking): non-empty maps and lists expand across indented, `=`-aligned lines; short all-scalar lists stay inline (`ports = [80, 443]`); structural punctuation (`{} [] = ,`) is muted while scalar leaves carry the color. Both value sites go through it — `kvLines` for plain views (resolved config, effect new-state, outputs, module/datasource/import/refresh state) and `attrDiff` for before→after diffs, which reads like `tofu plan`: top-level keys are `=`-aligned, and a **create/destroy propagates its `+`/`-` marker onto every nested line** (a marked block indents children +4 and closes its brace +2, reserving the marker column). A scalar `~` stays inline as `old → new`; a collection `~` is header-marked and shows the *new* value expanded — full per-line recursive sub-diffing (mixed `+`/`-`/`~` inside one block) is a deliberate non-goal. The `marker` is threaded through `renderValue`/`renderMap`/`renderList` (empty string = the unmarked `kvLines` view). `fmtVal` stays the **scalar-leaf** formatter only (quoting, numbers/bools, and the `__cty_unknown__`/`__cty_sensitive__` sentinel masks — reused at every nesting level so masking never leaks); `capLines` bounds any single block. This was a deliberate move away from a config-only HCL renderer (upstream `hclwrite` was evaluated and rejected — it fixes only resolved config and reads as a different aesthetic than the rest of the timeline). Because scalar output is byte-identical to the pre-nesting behavior, the existing per-tool tests stay green and `TestRenderValueNesting` guards the new expansion.
- `examples_test.go` — integration checks against the sibling `turf-examples` repo (resolved via `$TURF_EXAMPLES_DIR`, else `../turf-examples`; **skips** when absent, so CI without that checkout stays green). Asserts the turf example skill (`cli/.turf/skills`) loads via `loadTurfSkills`, and the cagent example `turf.yaml` still parses against the pinned docker-agent (including `skills: true`).
- `turfskills.go` — discovers user-authored `SKILL.md` skills from turf-owned locations **only** (`<TURF_HOME>/skills/<name>/SKILL.md` and `<cwd>/.turf/skills/<name>/SKILL.md`), never cagent's default `~/.claude`/`~/.codex`/`~/.agents` dirs. turf scans and parses these itself (cagent's `skills.Load("local")` is hardwired to the ecosystem dirs, and its frontmatter parser is unexported), building `skills.Skill` values for cagent's `skillstool.New`. Project skills override global ones on a name collision; the working-dir location is exactly `<cwd>/.turf/skills` (no walk up the tree). Populates `Skill.Files` (which cagent's own local loader leaves empty) so `read_skill_file` is exposed and supporting files are listed. Parses scalar frontmatter (`name`, `description` required; `context: fork` and `model` passed through).
- `prompts.go` — thin trigger prompts for `up` and `destroy` subcommands. The detailed step-by-step procedures live in the turf MCP server as the `/up` and `/destroy` prompts; this file just produces the initial user message that points the agent at them.
- `logging.go` — `setupLogging()` configures turf's **own** process-wide `slog` handler. Called first in `PersistentPreRunE` (before anything else), it routes all logs to a rotating file at `<TURF_HOME>/turf.debug.log` (path via `turfHome()`, since `paths.SetDataDir` isn't redirected until the TUI starts) and **never to stderr**, so cagent's runtime logging can't paint over the Bubbletea alternate screen — the fix for "model error dumps log spew over the TUI." The file always captures **Warn and above** (cagent reports some failures only through slog — e.g. its "Empty assistant turn" warning when a model returns an empty response and the turn ends with no output; discarding those made such failures undiagnosable). `--debug` (env `TURF_DEBUG`) lowers the file level to debug. If the file can't be opened, logs fall back to discard (and the error is surfaced only under `--debug`). This is turf's in-process logging only — **independent of the `--log-*` flags**, which pass through to the separate `turf-mcp-server` subprocess.
- `root.go` — cobra root command, all persistent flags (`--model`, `--mcp-server`, `--tmp-dir`, `--memory-path`, `--no-memory`, `--session-db`, `--no-session`, `--chdir`/`-C`, `--log-file`, `--log-level`, `--log-format`, `--theme`, `--debug`, `--lean`, `--allow-path`). `--allow-path` (env `TURF_ALLOW_PATH`, os.PathList-separated) is a repeatable string-slice flag (the CLI's only one) adding extra directories to the filesystem tool sandbox — and thus to the auto-approved area (file tools are pre-approved by name; see the tool-pre-approval note); relative entries resolve against the effective cwd, resolved via `envPathList`. `--lean` (env `TURF_LEAN`) opts into the lean TUI for the run (see `tui.go`/`runLeanTUI`); it is persistent so it covers `chat`, `up`, and `destroy` uniformly, and defaults off. The **resume flags** `--session <ref>` / `--continue`/`-c` are the exception — they are *local* (via `addResumeFlags` in `session.go`), registered on the bare root (which runs `runChat`) and on `chat`/`exec` only, so `up`/`destroy` never accept them (resuming onto a fresh `/up`|`/destroy` trigger prompt has no clean meaning). `PersistentPreRunE` calls `setupLogging()` (see `logging.go`) first, then honors `--chdir`. `--chdir` (git/make-style short alias `-C`) `os.Chdir`s before any subcommand runs, in `PersistentPreRunE`. The three `--log-*` flags are pass-throughs to `turf-mcp-server`'s flags of the same name; when unset, the server falls back to the `TF_LOG_*` env-var family (inherited via `os.Environ()` in `createAgentRuntime`). `--theme` (env `TURF_THEME`) is read by `applyTurfTheme()` and overrides the saved `/theme` choice for the run. Also defines the `appName` constant (`"turf"`), used to brand the TUI status bar / window title via `tui.WithAppName` in `tui.go`.
- `chat.go`, `up.go`, `destroy.go` — the three subcommands. `up` and `destroy` detect TTY and route to `runTUI` or `runExec` accordingly.
- `tui.go` — `runTUI` (interactive Bubbletea UI via cagent's `tui` package) and `runExec` (non-interactive via `cli.Run`). `runTUI` calls `applyTurfTheme()` before building the TUI, because cagent's `tui.New` does not auto-apply a theme, and passes `tui.WithAppName(appName)` + `tui.WithVersion(Version)` so the status bar / window title read "turf <version>" instead of cagent's "docker agent" default. `runTUI` takes the first message as a plain `string` (not an `app.Opt`) so it can route it to either TUI. When `--lean` (see `root.go`) is set, `runTUI` delegates to **`runLeanTUI`**, which drives cagent's standalone lean TUI (`pkg/leantui`) instead: it renders to the normal terminal buffer (no alternate screen), drops the sidebar/tab bar/overlays, and **owns its own input loop** — so it builds no `tea.Program` and needs no wheel coalescer. Three wiring differences from the full path: (1) it must `a.Start(ctx)` the app itself (the full TUI's model does this in `Init`); (2) leantui reuses the **same global tool-renderer registry** but never calls `tui.New`/`tui.WithToolRenderers`, so `runLeanTUI` registers turf's renderers directly via `registerTurfToolRenderers()` (see `renderers.go`); (3) leantui reads the first message from `leantui.Config.FirstMessage` (a `*string`), **not** `app.WithFirstMessage`, so the prompt is threaded into the `Config`. The lean welcome banner is **art, not derived from `AppName`** (unlike the full TUI's status-bar title): upstream leantui shows "docker agent" art, so turf brands it by passing its own `turfBanner` via `leantui.Config.Banner`. **That `Banner` field is a small turf addition to the cagent fork** (`pkg/leantui`, defaulting to the built-in art when unset) — the only fork change lean mode needs; everything else uses cagent's existing public API. `turfBanner` is a **hand-built pixel-font "TURF" wordmark** (brand greens, dark outline) — not figlet text and **not a downscale of the logo raster** (that read muddy) — built from `turfBannerArt`, an `//go:embed` of `assets/turf-banner.ansi`. That file draws the word in Unicode upper-half-block cells (`▀`): each character carries a truecolor **foreground = top pixel** and **background = bottom pixel**, so one text row shows two pixel rows (32 cols × 6 rows). It's authored from scratch by `assets/gen_banner.py` (Pillow-free), which holds the per-letter glyph bitmaps, auto-outlines the letter mass in dark green, and shades the body top→bottom (highlight → grass → shadow); **edit that script** to change the wordmark, don't hand-edit the `.ansi`. Background pixels use the terminal's **default color** (SGR `39`/`49`), so the wordmark blends with any theme background instead of sitting on a rectangle. The **load-bearing constraint** is that leantui wraps every banner line in a lipgloss `Foreground` style, and lipgloss only re-applies its own color *after an SGR reset*; so the generated cells are **switch-only (no mid-line reset)**, letting the real colors survive the wrapper (the accent color only paints leantui's 2-space leading pad), with a single reset ending each line. This means the banner needs a **truecolor terminal** — on 256-color terminals the embedded 24-bit sequences may be ignored or approximated. `leantui.Config` has no `Version` field, so lean mode has no version in its status footer, and (passing `service.StaticSessionState{}`, whose `HideToolResults()` is always false) no `Ctrl+O` tool-result toggle — turf's renderers always emit their expanded detail block. Theme still applies (leantui reads the same `styles` package `applyTurfTheme()` configures).
- `theme.go` — theming. `turfHome()` resolves turf's config home (`$TURF_HOME`, else `~/.turf`); `applyTurfTheme()` redirects cagent's process-global theme engine (`paths.SetDataDir`/`SetConfigDir`) at that home and applies a theme. Theme precedence (low→high): `defaultThemeRef`, a real saved `/theme` choice, then the `--theme` flag. `defaultThemeRef` is the single constant for turf's brand default.

**Model selection:** `--model` takes a `provider/model` string (e.g. `anthropic/claude-sonnet-4-6`, or the keyless local `dmr/ai/qwen3`). `newModelProvider()` in `agent.go` routes it through cagent's full provider factory — `providers.NewDefaultRegistry().New(...)`, the same registry cagent's own teamloader uses — rather than a hand-rolled switch. That registry dispatches to every provider cagent supports (cloud: openai/anthropic/google/amazon-bedrock; local: `dmr`/Docker Model Runner; plus OpenAI-compatible aliases ollama/mistral/groq/deepseek/xai/azure/…), filling in each provider's default base URL, token env var, and API type, and expanding `${env.*}` refs. An **unknown provider errors** here instead of silently falling through to OpenAI — surfacing a typo rather than hiding it behind a confusing "OPENAI_API_KEY required". `--base-url` (env `TURF_MODEL_BASE_URL`) sets `ModelConfig.BaseURL` to override the endpoint for arbitrary OpenAI-compatible servers (vLLM, LM Studio, gateways); DMR/Ollama resolve their own local endpoints and need none. On failure, `modelProviderError()` wraps the cause with actionable launch guidance that features the keyless local-model path and links Docker's providers overview — the "great error when turf can't launch" surface. Wiring the full registry pulls the bedrock factory's AWS SDK deps into `go.mod` (indirect).

**Memory:** Each session stores agent memory in a SQLite database (`.turf/memory.db` in the working directory by default). Disable with `--no-memory`.

**Session persistence (conversation history, distinct from Memory):** turf persists the *conversation itself* to a SQLite **session store** (`.turf/sessions.db` in the working dir by default; `--session-db`, env `TURF_SESSION_DB`), **on by default**, disabled by `--no-session` — the pair deliberately mirrors `--memory-path`/`--no-memory`, and the per-project location is chosen so both dbs live with the project. Both default under the turf-owned **`.turf/`** dir (`.turf/sessions.db`, `.turf/memory.db`) — the same dir that already holds project skills (`.turf/skills/`) — which keeps the project root clean and lets one turf-owned rule (`.turf/*` except `!.turf/skills/`) ignore all of turf's machine-local state at once; `.terraform/` was rejected as a home because it is disposable/OTF-owned and a routine `tofu init`/clean would wipe durable history. This is a different axis from Memory: Memory is the agent's advisory *knowledge* (facts it chooses to store via the memory tool); the session store is the raw transcript. **Session anchoring under `--worktree`:** the session store is the one thing that does *not* follow cwd into a throwaway worktree. The mental model is `--chdir` → **anchor** → worktree: `--chdir` runs first (in `PersistentPreRunE`) and defines the anchor (the launch dir); the session store lives at the anchor; the worktree is derived from it. So `.turf/sessions.db` is pinned to the real project's launch dir, while memory (`.turf/memory.db`), the recorded session `WorkingDir`, and the inherited `turf-mcp-server` cwd all follow cwd *into* the worktree — a unified session history across a project's throwaway worktrees, with the transcript surviving a worktree that is later removed. Mechanically, `setupRunWorktree` (`worktree.go`) captures the anchor (the pre-worktree cwd) and returns it as a second value; the run commands thread it to `createAgentRuntime` as `agentOpts.sessionDBDir`, which resolves the default session path to `<anchor>/.turf/sessions.db` (an explicit `--session-db` still wins; with no worktree the anchor is `""` and the store falls back to cwd, byte-identical to before). Note the anchor is the *invocation dir*, not the git repo root — launching from a subdirectory anchors history there, not at the repo top. turf's generated `.gitignore` (the turf-mcp-server plot/`config_init` scaffold, `plotfile.GitignoreStub`) ignores everything under `.turf/` except the committed `.turf/skills/` (`.turf/*` + `!.turf/skills/`) so none of turf's machine-local state is committed — the dbs, their SQLite `-wal`/`-shm` sidecars, and the persistent `memory.lock` advisory lock (which cagent's memory file-lock leaves on disk after unlock). The mechanism is almost entirely cagent's: `createAgentRuntime` (`agent.go`) opens the store via `session.NewSQLiteSessionStore`, wires it with `runtime.WithSessionStore`, and closes it in the returned cleanup (the runtime never closes an embedder-owned store); cagent then **auto-registers a `PersistenceObserver`** that writes messages/summaries/errors lazily (empty sessions leave no row). `createAgentRuntime` returns the store as a new second value so callers can resolve a resume ref *before* the session is built. **Resume:** `resolveTurfSession` (`session.go`) takes the `--session`/`--continue` ref (via `resumeRef`, which folds `--continue`→`-1` and rejects a ref under `--no-session`), resolves it with `session.ResolveSessionID` (concrete ID or relative offset like `-1` = most recent) + `store.GetSession`, and **re-applies turf's `applyTurfSessionPolicy` on the loaded session**. That policy (extracted from `newSession`) sets the session-level flags tools-approved + `HideToolResults(false)`, matching what cagent's own resume path already re-applies — so the resumed session's display/approval flags reflect the current run. Note **tool pre-approval is no longer a session-level concern**: it is installed once at the **team level** (see the tool-pre-approval note below), which is a property of the runtime rather than of any single session, so a resumed session inherits it automatically without a per-session re-stamp. An explicit, not-yet-existing ID creates a session bound to that ID (via `WithID`), so a script driving `exec` can own the ID across turns. Resume covers **`chat` + `exec`** only; `up`/`destroy` still persist (and appear in the browser) but stay one-shot. `newSession` also stamps `session.WithWorkingDir(cwd)` — cagent leaves that field empty unless the embedder sets it, and the browser groups sessions by it ("This workspace" vs elsewhere), so without it turf's sessions never grouped under the dir they were created in. The **full TUI's `/sessions` browser lights up for free** once the store is wired (`app.SessionStore()` → `handleOpenSessionBrowser`); the **lean TUI has no browser**, so lean resume is flag-only. **No tabs (single-session, working-dir oriented like Terraform) + browser-load fork patch:** turf runs single-session — it passes `spawner=nil` to `tui.New`, so it never surfaces tabs. Several `pkg/tui/tui.go` fork patches make that coherent, all keyed off a new `m.tabsEnabled()` helper (`supervisor.Spawner() != nil`): (1) every tab affordance is suppressed when there is no spawner — the "+ new tab" status-bar button (both `SetShowNewTab` sites), the `Ctrl+t/w/p/n` keybindings and their `AllBindings`/help entries, and the `NewSessionMsg` (`/new`) and `ForkSessionMsg` (`/fork`) handlers are no-ops — so nothing advertises a capability that isn't there. The fork **also auto-drops the tab-only commands (`/new`, `/fork`) from the command palette, parser, and completion** via `disableTabCommands()`, called at the end of `tui.New`, which adds them (the `tabOnlySlashCommands` list) to the shared `WithDisabledCommands` map when `!tabsEnabled()` — so the single `commandCategories()` choke point (which feeds all three) strips them, and a single-session embedder needs no opt-out of its own (deliberately fork-side rather than a turf `tui.WithDisabledCommands` call). `/clear` is deliberately **not** suppressed — it resets the current view in place and needs no spawner. (2) `handleLoadSession` loads a browser-selected session **in-place** when there is no spawner (`m.supervisor.Spawner() == nil`), instead of spawning a new tab and failing with "session spawning is not available" (the pre-patch behavior: loading a session mid-conversation did nothing); the current session is already persisted, so replacing it loses nothing. **Workspace-scoped browser (single-dir-per-process):** turf is deliberately one-working-dir-per-process, so a session created in a *different* dir can't be re-rooted here (cagent's respawn path would need the nil `Spawner()`). Rather than list such sessions and then decline them — and rather than introduce a spawner, which would both re-enable tabs (tab affordances gate on `Spawner() != nil`) and imply a *second* `turf-mcp-server` subprocess + store per loaded dir (the server binds the process cwd) — the browser is simply **scoped to the current workspace** for single-session embedders. `handleOpenSessionBrowser` passes `dialog.WithWorkspaceScoped()` when `Spawner() == nil`, which locks the browser's workspace filter to this-dir-only and disables the `Ctrl+G` toggle, so cross-dir sessions never appear and there is no load path to guard against in the first place. In normal use this is a no-op (the per-dir store already holds only current-dir sessions); it bites under `--worktree`, where the anchor store accrues past runs whose `WorkingDir` is a (now-ephemeral) worktree — those stay hidden, which is also forward-compatible with resumable worktrees (resuming one makes it the current workspace, so its sessions surface). `replaceActiveSession`'s respawn is still guarded on a non-nil `Spawner()` as a backstop for the internal restore callers (they'd otherwise panic on the nil call). `WithWorkspaceScoped` is a small variadic fork option so the 17 existing browser-dialog test callers stay unchanged. A second fork patch (`pkg/tui/dialog/session_browser.go`) fixes an empty `/sessions` browser: cagent hid every session with an empty `Title`. A turf session can legitimately be untitled — a chat-only session with no infra tool gets no deterministic title (see **Session titling** below) — so keying visibility on the title dropped real sessions and the browser looked empty even though `--continue` and `GetSessionSummaries` worked. The patch keys the "non-empty" filter on `NumMessages > 0` instead of `Title != ""`, so real-but-untitled sessions show (rendered as "Untitled"). Pre-approval survives browser load (and `/clear`, `/new`, `/fork`) because it lives at the **team level**, not on the session — so it does not depend on any persisted session column. `mcptoolset_test.go`-style drift is guarded by `session_test.go`.

**Session titling (`sessiontitle.go`):** the **`sessionTitleCurator`** — a `runtime.EventObserver` registered via `runtime.WithEventObserver` in `createAgentRuntime` — owns titling **end-to-end**, composing titles **deterministically** (no LLM). turf does **not** wire cagent's built-in LLM titler (`app.WithTitleGenerator` is not passed in `tui.go`), and an earlier turf LLM-summarizer was removed too: cagent's one-shot forces `WithNoThinking()` + `max_tokens=20`, which **400s on turf's default model** (`google/gemini-pro-latest` — Gemini 2.5 Pro rejects `thinkingBudget=0`), and even a thinking-tolerant LLM call **mis-stated the resource counts** (it would invent "4 resources" / lift "force replace" from the trigger prompt). So titles are now built from what turf *actually did*, in the **`terraform plan` glyph idiom**: `<alias> · init` after `config_init`, then `<alias> · plan +A ~C -D`, `<alias> · applied +A ~C -D`, `<alias> · destroyed -D`, `<alias> · promoted`. The counts come from `titleDigest.tallyPlan`, which buckets each plan resource's `action`, parsed from the **same renderer view structs** the TUI plan view uses (`configInitView`/`planSummaryView`/`resourcePlanEntry`/`planApproveView`/`effectApplyView`) — so a title's numbers always match the real plan. Following the terraform convention, a **replace** counts as **one add + one destroy** (`+1 ~0 -1`), not a change; `~` is reserved for genuine in-place updates. `isDestroy()` (pure-delete plan) picks the teardown wording; `configAlias` derives the label from the workspace name or config-path base (falling back to the cwd base for a `"."` path). The **digest evolves** across `ingest` calls: `config_init` sets the alias, `plan_new`/`replan` tally + set `stagePlan`, `plan_approve` records `effect_count`, and the **last** `effect_apply` of the approved plan (applied count reaches `effect_count`) flips to `stageApplied` — so a partial apply leaves the title unchanged. **Synchronous + cheap:** `OnEvent` parses, updates the digest under `mu`, recomputes `title()`, and writes only when it differs from `sess.Title` — no LLM means no goroutine/`seq`/stale-drop machinery. It acts only on the **root session** (pinned at the first `OnRunStart`), ignoring delegated sub-session tool activity. A **chat-only session** (no turf tool → no deterministic signal) stays *Untitled* by design (the browser's `NumMessages > 0` filter renders it fine). **Persistence + live refresh (one `setTitle` sink):** always `store.UpdateSessionTitle` (durable — `/sessions` browser, resume, headless `up`/`destroy`) plus, when the interactive TUI installs an **emitter** (`runTUI`/`runLeanTUI` set it to `go a.UpdateSessionTitle(...)` after the app is built), the `SessionTitleEvent` the sidebar/window title read (the store write alone doesn't live-refresh). `createAgentRuntime` returns the curator so the TUI can wire that emitter; headless callers pass `_`. Because `app.WithTitleGenerator` is unwired, `/title` *regenerate* (no-arg) is inert; `/title <text>` (and the sidebar edit) manual-set still works — and **wins**. Ownership is **stateless** (no flag/baseline): the curator overwrites only a title it could have produced itself — empty or one matching `isAutoTitle` (a package regex covering every `title()` shape *including* the `· init` pre-plan title, so there is no bare-alias special case; kept in lock-step with `title()` by the `TestAutoTitlePattern` invariant) — and never downgrades an existing milestone title back to `· init` (guarding the `config_init`-on-resume case, the one remaining stage check). Anything else is treated as human and left alone, which also means a human title **survives resume** (a prior-process human title doesn't match the auto pattern, so it's preserved; a prior auto title does, so new milestones still update it). The tracked tools are `titleCuratorTools`, tied to the live server tool set by a drift guard in `sessiontitle_test.go` (mirrors `permissions_test.go`); digest/format/gating are unit-tested against exact title strings, and `session_test.go` guards that a curator title survives resume.

**Telemetry (opt-out via `--no-telemetry`):** cagent ships anonymous usage telemetry **on by default** (env `TELEMETRY_ENABLED`, default true; events POST to `api.docker.com/events/v1/track` with a hardcoded key — session start/end, tool calls, token usage/cost, errors, plus a persistent install UUID, OS, version, language; no prompts/responses/file contents). turf keeps that default but exposes a first-class opt-out: `--no-telemetry` (env `TURF_NO_TELEMETRY`), mirroring `--no-memory`. It is implemented **env-var only** — `PersistentPreRunE` (in `root.go`) does an early `os.Setenv("TELEMETRY_ENABLED", "false")` *before* any subcommand builds the runtime or launches the subprocess, so it covers `chat`/`up`/`destroy` uniformly and propagates to `turf-mcp-server` via the `os.Environ()` handoff in `agent.go`. It only ever force-*disables*: when the flag is unset turf never writes the var, so an explicit user `TELEMETRY_ENABLED=false` is still honored. Note the client is attached to the runtime context only on the `cli.Run` exec path (cagent `pkg/cli/runner.go`), which is turf's non-interactive `runExec` (`up`/`destroy` without a TTY); the **interactive TUI** (`runTUI`/`runLeanTUI`) never attaches a client, so it emits no runtime telemetry regardless. Deliberately no structural `runtime.WithTelemetry(noop)` sink — the env var is the single lever (cagent reads it at telemetry-client init in `pkg/telemetry/utils.go`). cagent's own first-run telemetry banner and getting-started **tour** offer live in cagent's `cmd/root` and are never wired by turf's own `root.go`, so they don't appear.

**MCP server resolution:** `resolveMCPServer()` checks `--mcp-server` / `TURF_MCP_SERVER` first, then PATH for `turf-mcp-server`.

**Builtin toolset wiring (and what's left out):** `createAgentRuntime` wires four of cagent's builtin toolsets — `think`, `todo`, `memory`, `filesystem` — plus the MCP toolset and (conditionally) user skills. The selection is deliberate, not default: each wired tool fills a **distinct, non-competing slot**, and the authoritative "what to do" is always the **OpenTofu plan computed server-side by `turf-mcp-server`**, never an agent-side artifact. The mental model:
- `think` — what turf is *reasoning*. In-process, within-turn, zero side effects, asserts nothing (`ReadOnlyHint`). Pure pre-action scratchpad ("validate planned actions before executing") that *feeds* the plan. Safest possible tool; can't go stale, can't diverge from reality.
- `todo` — what turf is *doing right now*. In-memory, per-session step checklist. No persistence, no authority.
- `memory` — what turf *knows*. Persistent SQLite (`.turf/memory.db`); durable, **advisory** knowledge (preferences, decisions, conventions). Used silently to *inform* planning; orthogonal to the plan. A stale memory degrades gracefully (it's weighed against reality, never an instruction to act).
- `filesystem` — what turf *reads and authors on disk* (HCL, plan/state scaffolding). **Hard-sandboxed** to an allow-list of roots — the working dir, the scratch/`--tmp-dir` dir, and any `--allow-path` — via a symlink-hardened `*os.Root` (`allow` is assembled in `createAgentRuntime`; a symlink inside a root cannot escape it). This is turf's *only* agent-side write surface, and the sandbox is its blast-radius boundary; the `turf-mcp-server` subprocess does its own I/O outside it. All filesystem tools are pre-approved by name (see the tool-pre-approval note), so operations within the sandbox never prompt while nothing outside it is reachable.
- The **OpenTofu plan** (server-side) owns "what turf *will do*" — the single source of truth, reconciled against live infra state.

cagent's `tasks` toolset (`create_task`/`next_task`/dependency DAG, persistent `tasks.json`) is **deliberately NOT wired.** It is the one builtin that doesn't get its own slot: it stores persistent *actions* (not knowledge), and so competes with the OpenTofu plan as a second, unreconciled "what to do." For an infra tool that is dangerous — a stale persisted task ("create the bucket") is an instruction to mutate, and unlike OpenTofu state it never refreshes against reality; `next_task` also nudges toward autopilot, against turf's per-plan approval gate. `todo` already covers the in-flight checklist need. Revisit `tasks` only if turf grows an explicit multi-session *campaign / change-backlog* feature, and if so scope it to that (its own storage under `~/.turf`, persona wording that keeps it a notepad, not an autopilot) rather than enabling it for ordinary `up`/`destroy`.

**`--worktree` (wired narrowly for HCL authoring):** cagent's CLI ships two run-isolation wrappers — `--worktree` (a **git** boundary via `pkg/worktree`) and `--sandbox` (an **OS/process** boundary via `pkg/sandbox`). Both are host-process wrappers, not agent tools (the model can't invoke them); cagent sets up the isolation *before* launching the agent. Neither addresses turf's real blast radius — **OpenTofu mutating live cloud infrastructure via the `turf-mcp-server` subprocess** — which is instead governed at the OpenTofu **state/workspace + approval** layer (separate state, plan-then-approve, scoped credentials), the goal of the server's `/up`/`/destroy` flows. turf therefore leaves `--sandbox` unwired (a naive sandbox would more likely *break* turf — trapping the server subprocess + provider downloads and blocking the cloud-API calls that are its whole purpose — than secure it). **`--worktree` is the one narrow exception, now wired** (`worktree.go`): under the design where the server writes synthesized HCL directly into the working directory, drafting that generated config on a throwaway git branch is genuinely useful — the "HCL-authoring mode" this note used to reserve. It isolates only *config authoring*, not live infra. Mechanics: `--worktree[=name]` / `--worktree-base <ref>` are persistent flags (cover `chat`/`up`/`destroy`); `setupRunWorktree` creates the worktree from the current working dir (branched off `--chdir`) under `<TURF_HOME>/worktrees/<name>` via `worktree.WithRoot(turfHome())`, then **`os.Chdir`s into it before the runtime is built** — the single lever that redirects everything, because the `turf-mcp-server` subprocess inherits the CLI cwd (turf passes `cwd=""` to `NewToolsetCommand`), as do the filesystem tool's allow-list and the memory-db default. Teardown (`cleanupRunWorktree`) mirrors cagent: interactive-only, clean worktree auto-removed, dirty one prompts (default keep); the non-interactive `up`/`destroy` exec paths never remove it. The active branch is folded into the TUI status title (`versionWithBranch`/`appNameWithBranch` in `tui.go`). `--worktree-pr` is deliberately not exposed (PR continuation is a weak fit for infra authoring, though `pkg/worktree.CreatePR` supports it). Note `worktree.Create` requires an existing repo (`ErrNotGitRepository`); a future `git init`/commit helper (via the scoped shell tool) would be the complementary no-repo path.

**Secret handling (cagent `redact_secrets` deliberately OFF):** `createAgentRuntime` sets `agent.WithRedactSecrets(false)` explicitly. cagent only defaults this feature *on* through its YAML/teamloader path; turf builds the agent in code and bypasses that, so the field is already `false` — the explicit call records the decision rather than leaving it to an implicit default. cagent's `redact_secrets` is **pattern-based** (regex over known credential shapes — cloud keys, tokens, PATs) applied across tool args, pre-LLM messages, and tool output. For an infra tool that net is wrong in both directions: it misses arbitrary-shape secrets (a random DB password, a provider token matching no pattern — exactly what fills tfstate) and its effects on plan/state-heavy workflows are an unknown we don't want to absorb here. The intended, authoritative mechanism instead lives in the **`turf-mcp-server` via OpenTofu-native sensitivity** — values OTF marks `sensitive` (schema/variable/output marks, propagated through expressions; surfaced as the `after_sensitive`/`sensitive_values` parallel structures in plan/state JSON, or `cty` marks in-process). That is structural, not heuristic: it knows a leaf is secret regardless of shape, with near-zero false positives, and is the only place with the metadata to do it correctly. The design principle is mask-on-output / retain-for-execution (redact what reaches the model + transcript; keep the real value server-side for the provider). If that server-side handling ever lands and we still want a backstop for *unstructured* leaks (provider-authored error strings, model-fabricated echoes), revisit the flag then — but it is secondary to, not a substitute for, native sensitivity. Note also the `turf-mcp-server` `TF_LOG`/stderr sink is outside both mechanisms (provider debug logging can spill cleartext) — a separate hardening, not covered by either.

**Tool pre-approval (all turf tools run without a prompt; the agent confirms):** `createAgentRuntime` (in `agent.go`) installs a **team-level** permission checker — `team.WithPermissions(permissions.NewChecker(&latest.PermissionsConfig{Allow: preApprovedTools()}))` — where `preApprovedTools()` (in `permissions.go`) is the union of `preApprovedTurfTools` (**every** turf tool) and `preApprovedBuiltinTools()` — the cagent builtin toolsets turf trusts, kept as per-toolset lists each tied to its package's `ToolName*` constants by a `permissions_test.go` drift guard: **memory** (`preApprovedMemoryTools` — the advisory-knowledge store), **filesystem** (`preApprovedFilesystemTools`), and **todo** (`preApprovedTodoTools`). `Ask`/`Deny` are left empty. The permission layer therefore never prompts for a turf tool or a wired builtin. (`think` is not listed — it's a single, pure, read-only tool that already auto-approves via `ReadOnlyHint`; `todo`'s tools also carry `ReadOnlyHint` but are listed anyway, both for explicit trust and so a future hint change doesn't start prompting.) **Filesystem tools are pre-approved BY NAME, not by arg-scoped path patterns**, because the toolset is already hard-sandboxed to its allow-list roots — the working dir, the scratch/`--tmp-dir` dir, and any `--allow-path` — via a symlink-hardened `*os.Root` (built in `createAgentRuntime`). That sandbox, not the permission layer, is the real boundary: a file tool physically cannot touch anything outside the allowed roots, so pre-approving the writers (`write_file`/`edit_file`/`create_directory`/`remove_directory`, which lacked a `ReadOnlyHint`) only removes a prompt for work already confined to the sandbox, and **`--allow-path` widens the auto-approved area simply by widening the sandbox** — no separate permission wiring. (Arg-scoped patterns like `write_file:path=<cwd>/*` were rejected: the `paths` **array** args of `create_directory`/`remove_directory` stringify to `[...]` and never match a path glob, and models may pass relative paths a `<cwd>/*` prefix won't match — the capability sandbox is the correct, robust boundary.) **Team-level, not session-level, is load-bearing:** the dispatcher consults session-then-team permission checkers, and the team checker is a property of the runtime that outlives any single `session.Session` — so pre-approval survives session replacement (`/clear`, `/new`, `/fork`) and resume by construction, with no per-session re-stamp. (An earlier design stamped `session.WithPermissions` per session; that silently dropped the allow-list on `/clear`, since cagent's `App.NewSession()` preserves only tools-approved/hide-tool-results/working-dir — moving to the team level fixed that at the root and removed the resume re-stamp workaround. `permissions.go`/`permissions_test.go` carry the details.) This is a deliberate move away from the old plan-then-approve *permission* gate (which kept `effect_apply`/`action_invoke`/`effect_cancel`/`workspace_delete`/`resource_import`/`resource_refresh` behind `Ask`): that gate double-prompted right after the user had already answered the `user_prompt` "Approve plan?" dialog, friction on the tools that are the heart of the UX. Confirmation instead moves **into the agent**, guided by the persona (`workflowInstructions` in `agent.go`), in two shapes — **phase convergence** seeks one `user_prompt` yes/no *before* `plan_approve` summarizing the whole plan, then applies effects without prompting per `effect_apply`/`effect_cancel`; **standalone consequential ops** (`workspace_delete` — with an irreversibility warning — `resource_import`, `config_promote`, a directly-invoked `action_invoke`) get their own targeted `user_prompt` per call. `resource_refresh` is a benign state reconcile and needs no confirmation. **Why this stays safe:** the turf-mcp-server still faithfully annotates each tool `destructiveHint`/`readOnlyHint` (the structural core is unchanged — the "MCP" layer is just an implementation detail the CLI showcases over); the load-bearing property is now that `preApprovedTurfTools` is an explicit, static, **`turf_`-prefixed** enumeration (cagent prefixes every server tool because the MCP toolset is registered under the `turf` name), *not* a blanket `turf_*` prefix match — so a new/unknown turf tool, or any third-party MCP tool the CLI may load in future, is absent from `Allow` and still prompts (fail-safe: worst case is over-prompting, never under-prompting), and the drift test fails CI until it is consciously classified. `agentConfirmTurfTools` (also in `permissions.go`) is a documentation + drift-guard subset naming the tools the persona must confirm; it is deliberately **not** a mirror of `destructiveHint` (it includes non-destructive-but-consequential `effect_cancel`/`resource_import`, and excludes the destructive-but-authorizes-nothing-new `workspace_close`). `permissions_test.go` ties it to the live server: every server tool must be pre-approved (completeness), and every *server-destructive* tool must be either in `agentConfirmTurfTools` or the explicit `destructiveNoConfirm` carve-out (`{workspace_close}`) — so a newly-destructive server tool forces a confirmation decision. cagent's approval precedence: yolo (`--auto-approve`) > session `Allow`/`Ask` > **team `Allow`/`Ask`** (where turf's pre-approval now lives) > `ReadOnlyHint` > default `Ask` — the first checker to return a verdict wins (see `runtime.tool_dispatch` / `toolexec.Decide`), so `--auto-approve` still approves everything and read-only tools still auto-approve regardless of the list.

**Skills:** Two parallel mechanisms, kept non-colliding **by the `turf_` tool prefix**. (1) The turf MCP server vends `skill_core`/`skill_adhoc`/`skill_codified` (the built-in infrastructure workflows) — but, because the MCP toolset is registered under the `turf` name (see `agent.go`), the model sees these as `turf_skill_core`, etc. (2) Users author their own skills as `SKILL.md` directories, surfaced via cagent's **unprefixed** `read_skill` / `read_skill_file` / `run_skill` tools (`turfskills.go`). **The prefix is load-bearing, not cosmetic:** the turf MCP server *also* exposes a `read_skill_file` (slug-based, for its own skill attachments) that collides by name with cagent's user-skills `read_skill_file` (skill_name-based). Two tools sharing a name make a provider reject the entire request — Gemini returns `400 "Duplicate function declaration found"`, which is fatal to every turn. The `turf_` prefix de-collides them (`turf_read_skill_file` vs `read_skill_file`); cagent strips the prefix before dispatching, so the server still sees the bare name. Each user skill is a directory: `<root>/skills/<name>/SKILL.md` with YAML frontmatter declaring at least `name` and `description`; supporting files (e.g. `references/*.md`) load on demand. Roots, low→high precedence: `<TURF_HOME>/skills` (global — org best practices, migration playbooks) then `<cwd>/.turf/skills` (project, versioned with the infra config). Skills with no frontmatter are skipped (that is why the *server's* skills, which lack frontmatter, only work through `turf_skill_*`, not `read_skill`). The toolset is wired only when at least one skill is found, so a user with none pays nothing.

**Theming:** The TUI ships with a distinctive default theme (`calm-roots`, set via the `defaultThemeRef` constant in `theme.go`). Themes load and persist from turf's own config home — `~/.turf` (override with `TURF_HOME`), never `~/.cagent`. `--theme <name>` (env `TURF_THEME`) overrides the applied theme for a single run without changing the saved `/theme` choice. To add a custom theme, drop a YAML at `~/.turf/themes/<name>.yaml` and select it in the TUI with `/theme`; edits hot-reload while the picker is open, and the choice survives restart. A partial YAML is merged onto the built-in default, so you only need to specify the colors you want to change. A fully custom turf-branded theme baked into the binary is a tracked follow-up (see the TODO in `theme.go`).
