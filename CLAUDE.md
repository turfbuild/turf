# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```sh
make build      # compile to bin/turf (embeds git-derived version)
make test       # go test ./...
make fmt        # go fmt ./...
make vet        # go vet ./...
make tidy       # go mod tidy
```

Always build with `make build`, not `go build` — the Makefile injects the git-derived version via ldflags, which a bare `go build` omits.

Run a single test:
```sh
go test -run TestName ./...
```

Release gate: `docs/testing/release-gate.md` — the manual suite run against a release's draft tarball before it is published (a real terminal, a real model, the live drift tests CI skips).

## Architecture

`turf` is a thin CLI wrapper around the `turf-mcp-server` binary. It never imports turf server code — the only contract is MCP over stdio.

**On `github.com/opentofu/svchost` (a direct dep — do not "fix" this):** that rule is about the *doof / turf-mcp-server* boundary, and `svchost` is not turf server code. It is a standalone public OpenTofu library (its own module path, no dependency on OpenTofu core) that `turf-mcp-server` **already** imports (`doof/cmd/turf-mcp-server/main.go`), so taking it aligns both halves of the product on one service-discovery library. `login.go`/`credentials.go` need it because three of the four things that determine `tofu` interop live in it: `ForComparison`/`ForDisplay` hostname normalization (~250 lines of IDNA/punycode, and the credentials-file **map key** is `ForDisplay()` output, so a one-codepoint divergence means `tofu` cannot find what turf wrote), `login.v1` parsing, and the discovery request's exact semantics (media-type check, 1 MiB cap, `404` → zero services, 3-redirect bound). Dep weight is ~zero: its four requires (`go-cmp`, `go-cty`, `x/net`, `x/oauth2`) were all already in turf's graph at higher versions, so it added exactly one `go.mod` line and changed no other version. Hand-rolling would mean ~450 lines of security-adjacent, upstream-tracking code to save that line.

**Data flow:**
```
CLI (cobra commands) → createAgentRuntime() → cagent runtime → turf-mcp-server subprocess (MCP/stdio)
                                                             → OpenTofu providers (downloaded on demand)
```

**Key files:**
- `agent.go` — constructs the cagent runtime. Launches `turf-mcp-server` as a subprocess, wires up toolsets (MCP tools, filesystem, think, todo, memory, and — when present — user skills), and creates the cagent `agent`/`team`/`runtime`. Registers the MCP toolset under the **`turf` name** so cagent prefixes every server tool with **`turf_`** (e.g. `turf_skill_deployment`, `turf_read_skill_file`) — see the Skills note below for why. Contains `workflowInstructions`, a short persona that delegates workflow guidance to the MCP server's instructions and `turf_skill_*` tools, spells out the `turf_` prefix mapping (the server names its own tools bare), distinguishes those from user `read_skill` skills, and carries the **dispatch-ordering note** — batched tool calls execute sequentially in emission order, so the persona tells the model to order dependent calls correctly within a batch and to await a call's *result* before emitting a call whose arguments need it. Sequential execution comes from `runtime.WithSequentialToolCalls(true)` at `runtime.New`, a **cagent fork patch** (upstream ≥ v1.99.0 fans a model batch out in parallel, unconditionally — which raced turf's stateful, order-dependent planning tools into ordering errors; prompt-only discipline proved insufficient). The API-level `parallel_tool_calls=false` knob was rejected: only the OpenAI/DMR providers honor it (Gemini, turf's default, ignores it) and it costs one LLM round-trip per call, while dispatcher-side serialization keeps multi-call batching free. Drop the fork patch when upstream ships its planned tool-execution-strategy config.
- `mcptoolset.go` — `turfMCPToolset`, a thin decorator around the MCP toolset that improves how turf's tools present in the **`/tools` dialog**. `Tools()` files each tool under a functional sub-category (`turf · config`, `turf · workspace`, `turf · run`, `turf · apply`, `turf · state`, `turf · provider`, `turf · skills`) and gives it a friendly, verb-first **display** name (`turf_apply` → "Apply Plan", `turf_up` → "Deploy", the engine console's word for its run kind) via `Annotations.Title`, instead of one flat `turf` group of raw `turf_*` ids. Both come from `turfToolInfo`, the per-tool source of truth. Display-only — the model still calls `turf_*`; providers and permissions key on `Name`. The tool set (group + title) is kept in lock-step with the `permissions.go` lists by `mcptoolset_test.go`. `Kind()` masks the inner `MCP` classification so turf reads as a built-in capability, not an external MCP integration. The dialog itself (layout, sorting, **description truncation**) is owned by cagent and not customizable without forking, so these data-side fields (`Category`, `Annotations.Title`) are turf's only lever over it.
- `renderers.go` — custom TUI **timeline** renderers for every `turf_*` tool of the server's **v1 surface** (the Terraform-named tools on the Turf engine: `init`, `open`/`close`/`list`/`status`/`delete`, `up`/`destroy`/`refresh`/`import`/`invoke`, `apply`, `cancel`, `show`, `output`, `state_list`, `taint`/`untaint`, `provider_*`, skills): a one-liner that leads with the friendly `turfToolInfo` title, then target + colored status, with a Ctrl+O expand block. Plugs into cagent's renderer registry through the **same entry point its own built-ins use** — `tui.WithToolRenderers(map[string]tool.Builder)` → `tool.Register`, with `tool.Builder` + `toolcommon.NewBase` + `toolcommon.Renderer` — keyed by exact tool name. The renderer map comes from `turfToolRenderers()`; the full TUI wires it via `tui.WithToolRenderers`, while the lean TUI (which never calls `tui.New`) registers the same map directly through `registerTurfToolRenderers()` — both funnel through `tool.Register`, so lean and full render tools identically. Each `Renderer` is hand-written (not cagent's `SimpleRenderer`/`RenderTool`, which model a one-arg/one-result line) and parses `msg.Content` JSON (turf results cross the MCP boundary as text; `parseContent` is plain `json.Unmarshal`, so a renamed server field decodes as a zero value and the line quietly degrades rather than erroring). Every tool has a renderer and every renderer leads with its title — both enforced by `renderers_test.go`. **The vocabulary:** Terraform's where Terraform has a word — the plan glyphs in `planAction` are OpenTofu's `DiffActionSymbol` (`+ ~ - -/+ +/- ./+ <= .`, no glyph for a no-op), `(known after apply)`, `(sensitive value)` — and the Turf engine admin console's for Turf concepts Terraform lacks: a convergence's outcome (`converged` for a deploy, `done` for other kinds; `stalled`/`exhausted` · N deferred, `declined`, `cancelled` neutral; `failed` red), round statuses, and invocation verdicts (`invoked`, `skipped — its condition was false`, `failed · continued`, `failed · tainted its caller`). **Colors stay the CLI theme's own** (`planAction`: create `Success`, update `Accent`, delete `Error`, replace `Warning`, forget `Highlight`, read `Accent`) — the console's palette was deliberately not adopted. **The convergence family** (`up`, `destroy`, `refresh`, `import`, `invoke`, `apply`, `cancel`) shares one renderer, `renderConvergence` over `convergenceView` (a mirror of the server's `convergence.Result`): the compact line names the convergence and where it stands — `round N · +A ~C -D · … · awaiting approval`, `awaiting N action(s)`, or the ending with totals; `apply`/`cancel` lines also carry the run-kind word (deploy, refresh-only, …) since they act on a convergence an earlier call started; the expansion lists the vended plan's path/short digest/expiry, the invocations it schedules, the turf actions awaiting answers (key, prompt, if-failed, inputs, refusals — a refused answer with no open request, e.g. one sent after the convergence ended, gets its own `refused:` section and every summary counts refusals), each round with its failures, action outcomes, warnings and cancel cause, and the finalized/carried outputs. **Counts only, by decision:** the result carries the plan's counts (`plan.add/change/destroy/replace/import/forget/read/deferred/drift/outputs/invocations`, replace counted inside both + and -, as Terraform's summary counts it), not its resource changes; the per-resource plan is the document at `plan.path`, which the server deletes once the round applies and which the timeline does **not** read. **A convergence that did not converge arrives as an MCP error carrying the whole result** (`isError` for every outcome but `awaiting_*`/`converged`), so `renderConvergence` parses before deferring to `errorLine`; a refusal (stale digest, busy workspace) is plain text and stays an ordinary error line. cagent sends no `progressToken` and does not relay MCP progress notifications, so a running convergence line can only say what the call is doing (`planning…`, `applying…`, `answering actions…`). **`show`** is where per-resource diffs live: it returns OpenTofu's own `tofu show -json` plan (or state) document, redacted server-side, and `renderShow` renders each worthwhile `resource_changes` row (no-ops skipped unless adopting or moving) as a glyph header with short notes (`adopt id=…`, `moved from X`, `forces replacement: <replace_paths>`, the `action_reason`) over `attrDiff`, then `changed outside Turf` (drift), `deferred` (raw reasons, as the console shows them), output changes, and the invocations (the document's `BeforeCreate`/`ActionOnFailureContinue` respelled the configuration's way by `configSpelling`). Unknowns come from the document's `after_unknown`, overlaid onto `after` as the `__cty_unknown__` sentinel by `withUnknowns`, so `attrDiff`/`fmtVal` print `(known after apply)` with no unknown-aware code of their own (an `after` unknown as a whole reads as one `(known after apply)` line, never as a destroy). The surviving tools mirror their v1 shapes: `init` (installed version per required provider, built-in, or the install error; lock-file status; imports; provider configurations), `open`/`status` (the binding plus the **convergence holding the workspace**, rendered `holds p-… · deploy · awaiting approval · round 2` — what makes a re-attach legible), `close` (`detached`: the convergence it stopped following goes on in the engine), `output`, `state_list` (values under `include_values`, tainted/deposed/identity, outputs), `taint`/`untaint`, `provider_describe` (including the builtin turf provider's whole-schema form). **Failed tool calls surface the framework's error text** and **lead with the request's target**: on `ToolStatusError` the shared `errorLine` renders `msg.Content` red, prefixed by the target from `errorTarget` — a per-tool `turfToolTargetArgs` lookup (`convergence_id` for apply/show, `action_addr` for invoke, `addrs` for taint — `argString` joins a string list — …) with a universal `workspace_alias` fallback; expanded it wraps, compact it truncates with an ellipsis after the target. It reaches every renderer through `fallbackLine`, and `TestEveryRendererReportsErrors` guards that none regress to a silent bare line. **Rendering OTF values:** every JSON-decoded value funnels through `renderValue` (+ `renderMap`/`renderList`) in the `tofu plan` idiom — `=`-aligned `key = value`, nested maps/lists expanded, short scalar lists inline, structural punctuation muted; `kvLines` for plain views, `attrDiff` for before→after (a create/destroy propagates its `+`/`-` onto every nested line; a scalar `~` stays inline as `old → new`; a collection `~` is header-marked and shows the new value — full recursive sub-diffing is a deliberate non-goal). **Sensitivity masks (redaction is the renderer's job, not the server's alone):** `show`, `output` and `state_list` take `show_sensitive`, which puts the **real secret on the wire** deliberately so the model can use it; the timeline is also terminal scrollback and the persisted session, so turf redacts at *display* time from the mask whatever arrived — OpenTofu's `before_sensitive`/`after_sensitive`/`sensitive_values` shape (`true` covering a subtree, objects keyed, lists positional), threaded through `renderValue`/`renderMap`/`renderList` and checked **before** the type switch, so a marked node collapses to `(sensitive value)` without being descended into (and `maskKey`/`maskIndex` keep a sensitive node sensitive below it, so a whole-value `true` mask cannot leak its attributes through `attrDiff`); that is exactly what `fmtVal` prints the server's `__cty_sensitive__` sentinel as, so revealed and redacted read identically. An attribute masked on both sides normally drops out of a diff as unchanged; revealed, the renderer can prove it moved and renders `~ pw = (sensitive value) → (sensitive value)`. Outputs carry their mask as a per-output `sensitive` flag, which `outputsMask` turns into a `{name: true}` mask rather than flattening away. **Guards:** `TestTurfToolTargetArgsMatchServerSchemas` asserts every target arg names a real property of the tool's live `InputSchema` (via the `serverTools(t)` harness in `permissions_test.go`); **result** fields stay unguarded — the server publishes no output schema — so the per-tool tests, whose fixtures are the v1 server's own recorded results (the manual suite's smoke run on fixture `core`, plus `testdata/show-plan-core.json` and doof's every-action document `testdata/show-plan-every-action.json`), are the cover there.
- `examples_test.go` — integration checks against the sibling `turf-examples` repo (resolved via `$TURF_EXAMPLES_DIR`, else `../turf-examples`; **skips** when absent, so CI without that checkout stays green). Asserts the turf example skill (`cli/.turf/skills`) loads via `loadTurfSkills`, and the cagent example `turf.yaml` still parses against the pinned docker-agent (including `skills: true`).
- `turfskills.go` — discovers user-authored `SKILL.md` skills from turf-owned locations **only** (`<TURF_HOME>/skills/<name>/SKILL.md` and `<cwd>/.turf/skills/<name>/SKILL.md`), never cagent's default `~/.claude`/`~/.codex`/`~/.agents` dirs. turf scans and parses these itself (cagent's `skills.Load("local")` is hardwired to the ecosystem dirs, and its frontmatter parser is unexported), building `skills.Skill` values for cagent's `skillstool.New`. Project skills override global ones on a name collision; the working-dir location is exactly `<cwd>/.turf/skills` (no walk up the tree). Populates `Skill.Files` (which cagent's own local loader leaves empty) so `read_skill_file` is exposed and supporting files are listed. Parses scalar frontmatter (`name`, `description` required; `context: fork` and `model` passed through).
- `prompts.go` — `renderServerPrompt`, the single helper the `up`/`destroy` subcommands use to build their initial user message. It calls `rt.ExecuteMCPPrompt(ctx, "up"|"destroy", {config_path, auto_approve, instructions})` to **render the turf MCP server's own authored `/up`/`/destroy` prompt** — the *same* fork method (`runtime.Runtime.ExecuteMCPPrompt` → MCP `prompts/get`) the full TUI's `/up`/`/destroy` slash commands use, so the CLI subcommand and the slash command share **one content path**. `config_path` is passed **explicitly** (the subcommand's post-`--worktree`-chdir `absPath`) so the server never falls back to inherited cwd; `--yes`/`--auto-approve` sends `auto_approve: "true"` (the user pre-approved every plan of this run, so the server's prompt has `up`/`destroy` run to the end without pausing at each round's approval point); positional args to `turf up`/`turf destroy` are joined into the optional `instructions` argument (woven into the prompt's *User Instructions* section server-side, never bypassing approval) — `Args: cobra.ArbitraryArgs`, so `turf up replace aws_s3_bucket.assets` and `turf up -- -target=module.network` (the `--` form for dash-leading text) both work. Fail-fast: a `prompts/get` error is returned wrapped, not silently replaced by a fallback trigger. The rendered server prompt is a **thin, user-context kickoff** (per MCP semantics: `PromptMessage.role` is `user`/`assistant` only — no system role) that points at the server's skill carrying the step-by-step runbook, which the model pulls on demand — a deliberate MCP layering (prompt = user-controlled kickoff, skill = model-controlled reference, persona = system) that lives in the `doof` server; turf just renders whatever the server returns.
- `logging.go` — `setupLogging()` configures turf's **own** process-wide `slog` handler. Called first in `PersistentPreRunE` (before anything else), it routes all logs to a rotating file at `<TURF_HOME>/turf.debug.log` (path via `turfHome()`, since `paths.SetDataDir` isn't redirected until the TUI starts) and **never to stderr**, so cagent's runtime logging can't paint over the Bubbletea alternate screen — the fix for "model error dumps log spew over the TUI." The file always captures **Warn and above** (cagent reports some failures only through slog — e.g. its "Empty assistant turn" warning when a model returns an empty response and the turn ends with no output; discarding those made such failures undiagnosable). `--debug` (env `TURF_DEBUG`) lowers the file level to debug. If the file can't be opened, logs fall back to discard (and the error is surfaced only under `--debug`). This is turf's in-process logging only — **independent of the `--log-*` flags**, which pass through to the separate `turf-mcp-server` subprocess.
- `root.go` — cobra root command, all persistent flags (`--model`, `--mcp-server`, `--tmp-dir`, `--memory-path`, `--no-memory`, `--session-db`, `--no-session`, `--chdir`/`-C`, `--log-file`, `--log-level`, `--log-format`, `--theme`, `--debug`, `--lean`, `--allow-path`). `--allow-path` (env `TURF_ALLOW_PATH`, os.PathList-separated) is a repeatable string-slice flag (the CLI's only one) adding extra directories to the filesystem tool sandbox — and thus to the auto-approved area (file tools are pre-approved by name; see the tool-pre-approval note); relative entries resolve against the effective cwd, resolved via `envPathList`. `--lean` (env `TURF_LEAN`) opts `chat` into the lean TUI for the run (see `tui.go`/`runLeanTUI`) and defaults off; `up` and `destroy` on a terminal always run the lean TUI, whatever the flag says (they exit when the agent's turn ends). The **resume flags** `--session <ref>` / `--continue`/`-c` are the exception — they are *local* (via `addResumeFlags` in `session.go`), registered on the bare root (which runs `runChat`) and on `chat`/`exec` only, so `up`/`destroy` never accept them (resuming onto a fresh `/up`|`/destroy` trigger prompt has no clean meaning). `PersistentPreRunE` calls `setupLogging()` (see `logging.go`) first, then honors `--chdir`. `--chdir` (git/make-style short alias `-C`) `os.Chdir`s before any subcommand runs, in `PersistentPreRunE`. The three `--log-*` flags are pass-throughs to `turf-mcp-server`'s flags of the same name; when unset, the server falls back to the `TF_LOG_*` env-var family (inherited via `os.Environ()` in `createAgentRuntime`). `--theme` (env `TURF_THEME`) is read by `applyTurfTheme()` and overrides the saved theme choice (the full TUI's `/settings` → Appearance → Theme) for the run. Also defines the `appName` constant (`"turf"`), used to brand the TUI status bar / window title via `tui.WithAppName` in `tui.go`.
- `chat.go`, `up.go`, `destroy.go` — the three subcommands. `up` and `destroy` detect TTY and route to `runTUI` or `runExec` accordingly.
- `credentials.go` — the **OpenTofu credentials-file interop layer**, a deliberate port of upstream's `internal/command/cliconfig/credentials.go` rather than an independent design: `turf login` is only useful if a co-installed `tofu`/`terraform` reads back exactly what turf wrote, so path resolution, the read-modify-write, and the on-disk bytes all have to match. `credentialsDir()` mirrors `ConfigLoader.configDir` — `<home>/.terraform.d`, except a *fresh* install (that dir absent) with `XDG_CONFIG_HOME` set uses `$XDG_CONFIG_HOME/opentofu`; `%APPDATA%\terraform.d` on Windows (upstream calls `SHGetFolderPathW`; turf reads the env var with `os.UserConfigDir()` as fallback, to keep `syscall`/`unsafe` out of the CLI). Note this is a **stat-time decision**, and `tofu` honors the XDG path while HashiCorp `terraform` does not — so the consent prompt always prints the resolved path. `tofuHomeDir()` is `$HOME` then `user.Current()`, deliberately **not** `os.UserHomeDir` (which reads `USERPROFILE` on Windows, the wrong root here). `updateCredentialsFile` is the single surgical read-modify-write: decode the *whole* document with `json.Decoder.UseNumber()` (a large integer elsewhere in the file would otherwise degrade to `1.23e+19`), get-or-create `credentials`, **delete every key that `svchost.ForComparison`-normalizes to the target host** (so a differently-cased spelling is replaced, not duplicated), insert under `host.ForDisplay()`, then `json.MarshalIndent(raw, "", "  ")` — two-space indent and **no trailing newline**, matching tofu byte-for-byte and preserving unrelated top-level keys (`plugin_cache_dir`, `provider_installation`, other hosts). A nil token deletes, retaining an empty `"credentials": {}`; deleting from a nonexistent file is a no-op that creates nothing. Publish goes through `atomicfile.Write(path, r, 0o600)` (docker-agent) — upstream's temp-in-same-dir + rename + chmod, plus an fsync — after `os.MkdirAll(dir, 0o700)` (upstream lets `CreateTemp` fail on a machine that never ran tofu). The **chmod is load-bearing on rewrite**: the underlying `natefinch/atomic` copies the destination's existing mode onto its temp file, so a `0644` file would stay `0644` without it. A **punycode key is deliberately not swept** — tofu rejects punycode in a `credentials` block and ignores such an entry on read, so it denotes no host and can't collide. `envTokenVarForHost` mirrors `collectCredentialsFromEnv` for the shadow warnings: `"__"`→`"-"` **before** `"_"`→`"."` (unambiguous because a hyphen can't start or end a label), then the permissive `ForComparison(ForDisplay(...))` that — uniquely in turf — tolerates a pre-punycoded name, since env vars often can't carry unicode.
- `login.go`, `logout.go` — `turf login <hostname>` / `turf logout <hostname>`, emulating `tofu login`/`logout`. **Both require an explicit hostname** (`exactlyOneHost`, shared): tofu declines to guess a default (HashiCorp `terraform` defaults to `app.terraform.io`; OpenTofu deliberately does not, and neither does turf). The helper exists rather than `cobra.ExactArgs(1)` because the root sets `SilenceUsage`, so cobra's "accepts 1 arg(s), received 0" would print with no usage text to explain it. **The manual-token path is the primary one, not a fallback** — verified live, *no* real host publishes a `login.v1` block (`app.terraform.io`, `turf.scalr.io`, and `registry.opentofu.org` advertise only `tfe.v2`/`modules.v1`/`providers.v1` and friends), so the OAuth path exists for protocol completeness and is exercised only by test fakes. Flow order in `runLogin`: `--token-stdin` short-circuits everything interactive (consent is implicit — the caller piped the secret) → a non-TTY stdin without that flag **hard-errors naming the flag** rather than hanging (mirroring tofu's `-input=false` refusal) → discovery → `ServiceOAuthClient("login.v1")`, where *every* way of not advertising a usable client (absent, unsupported version, malformed, password-grant-only) falls through to the token path rather than failing → `tfe.v2` lookup → the `TF_TOKEN_*` shadow warning → **consent** (a literal case-insensitive `yes`, always before any browser opens or secret is typed, since it is the one gate before a plaintext secret hits disk) → obtain → store. `loginByCode` keeps only `access_token`; the protocol has no refresh, so `refresh_token`/`expires_in` are dropped. `listenerForCallback` binds `tcp4` `127.0.0.1` but advertises **`http://localhost:<port>/login`** — `localhost` not `127.0.0.1`, and no trailing slash — both quirks inherited from tofu and load-bearing, since hosts register the literal string; the port range is treated as **inclusive** (upstream's `max-min` span never selects `maxPort` and fails outright on a single-port range). `validateTFEToken` replaces go-tfe's `Users.ReadCurrent` with one `GET <tfe.v2>/account/details` + JSON:API headers, so go-tfe stays out of `go.mod`. Deliberate divergences from tofu: the callback **reports** an `error=`/`error_description=` denial instead of ignoring it and hanging until the 10-minute timeout; `oauth2.GenerateVerifier()` (crypto/rand) replaces upstream's `math/rand`-suffixed UUID verifier (invisible to the server, which only sees the S256 challenge); `--token-stdin` replaces a `--yes` that would buy nothing (both paths stay interactive anyway, and skipping consent would only suppress the disclosure of *where* the plaintext token lands); no MOTD fetch (a HashiCorp marketing surface needing control-char sanitization to render safely); no `password` grant (gated to `app.terraform.io` upstream and described in-source as "purely theoretical"); and **no `CredentialsInOtherFile` refusal**, which would need an HCL1 dep to parse `.terraformrc`/`.tofurc` — the failure mode of skipping it is benign (the hand-written block keeps winning) and is documented in the README and `Long` help. `logout.go` imports **only `svchost`** — not `disco`, not `net/http` — and that import list *is* the structural guarantee that logout never touches the network; `TestLogoutIsOffline` guards it behaviorally. Test seams: `openBrowser`, `stdin` + the shared `stdinLines` buffer (one reader for the whole run — a fresh `bufio.Reader` per prompt would read ahead past the consent answer and swallow the token typed after it), and `stdinIsInteractive`, kept **separate** from `promptSecret`'s own `term.IsTerminal` check so the echo-suppression decision stays honest under test while the flow still runs from a pipe. **Who consumes the file:** a co-installed `tofu`/`terraform` always does, and `turf-mcp-server` does as of doof `829b75d` (post-`v0.11.1`), which replaced the credential-less `disco.New()` in `cmd/turf-mcp-server/main.go` with `xcliconfig.NewServiceDiscovery` — feeding the `remote`-protocol backends and the provider installer, with the module installer following in `48f1a4b`. So one `turf login` now covers all three, but **only against a server newer than v0.11.1**; older servers write-and-ignore, which is what the README note and `Long` help carve out. Verified end to end against a live Scalr `remote` backend, including the negative control that `turf logout` makes `tofu init` fail with "Required token could not be found" and `turf login` makes it succeed.
- `tui.go` — `runTUI` (interactive Bubbletea UI via cagent's `tui` package) and `runExec` (non-interactive via `cli.Run`). `runTUI` calls `applyTurfTheme()` before building the TUI, because cagent's `tui.New` does not auto-apply a theme, and passes `tui.WithAppName(appName)` + `tui.WithVersion(Version)` so the status bar / window title read "turf <version>" instead of cagent's "docker agent" default. `runTUI` takes the first message as a plain `string` (not an `app.Opt`) so it can route it to either TUI. When `--lean` (see `root.go`) is set, `runTUI` delegates to **`runLeanTUI`**, which drives cagent's standalone lean TUI (`pkg/leantui`) instead: it renders to the normal terminal buffer (no alternate screen), drops the sidebar/tab bar/overlays, and **owns its own input loop** — so it builds no `tea.Program` and needs no wheel coalescer. Three wiring differences from the full path: (1) it must `a.Start(ctx)` the app itself (the full TUI's model does this in `Init`); (2) leantui reuses the **same global tool-renderer registry** but never calls `tui.New`/`tui.WithToolRenderers`, so `runLeanTUI` registers turf's renderers directly via `registerTurfToolRenderers()` (see `renderers.go`); (3) leantui reads the first message from `leantui.Config.FirstMessage` (a `*string`), **not** `app.WithFirstMessage`, so the prompt is threaded into the `Config`. The lean welcome banner is **art, not derived from `AppName`** (unlike the full TUI's status-bar title): upstream leantui shows "docker agent" art, so turf brands it by passing its own `turfBanner` via `leantui.Config.Banner`. **That `Banner` field is a small turf addition to the cagent fork** (`pkg/leantui`, defaulting to the built-in art when unset) — the only fork change lean mode needs; everything else uses cagent's existing public API. `turfBanner` is a **hand-built pixel-font "TURF" wordmark** (brand greens, dark outline) — not figlet text and **not a downscale of the logo raster** (that read muddy) — built from `turfBannerArt`, an `//go:embed` of `assets/turf-banner.ansi`. That file draws the word in Unicode upper-half-block cells (`▀`): each character carries a truecolor **foreground = top pixel** and **background = bottom pixel**, so one text row shows two pixel rows (32 cols × 6 rows). It's authored from scratch by `assets/gen_banner.py` (Pillow-free), which holds the per-letter glyph bitmaps, auto-outlines the letter mass in dark green, and shades the body top→bottom (highlight → grass → shadow); **edit that script** to change the wordmark, don't hand-edit the `.ansi`. Background pixels use the terminal's **default color** (SGR `39`/`49`), so the wordmark blends with any theme background instead of sitting on a rectangle. The **load-bearing constraint** is that leantui wraps every banner line in a lipgloss `Foreground` style, and lipgloss only re-applies its own color *after an SGR reset*; so the generated cells are **switch-only (no mid-line reset)**, letting the real colors survive the wrapper (the accent color only paints leantui's 2-space leading pad), with a single reset ending each line. This means the banner needs a **truecolor terminal** — on 256-color terminals the embedded 24-bit sequences may be ignored or approximated. `leantui.Config` has no `Version` field, so lean mode has no version in its status footer, and (passing `service.StaticSessionState{}`, whose `HideToolResults()` is always false) no `Ctrl+O` tool-result toggle — turf's renderers always emit their expanded detail block. Theme still applies (leantui reads the same `styles` package `applyTurfTheme()` configures).
- `theme.go` — theming. `turfHome()` resolves turf's config home (`$TURF_HOME`, else `~/.turf`); `applyTurfTheme()` redirects cagent's process-global theme engine (`paths.SetDataDir`/`SetConfigDir`) at that home and applies a theme. Theme precedence (low→high): `defaultThemeRef`, the co-brand's `branding.theme` (see the Co-branding note), a real saved theme choice (`/settings` → Appearance → Theme; there is no `/theme` command), then the `--theme` flag — so a distributor sets the *default* look while the user's own pick still wins. `defaultThemeRef` is the single constant for turf's brand default (`stadium`). turf **ships its own built-in themes** from `assets/themes/*.yaml` (`//go:embed` → `registerTurfThemes`, a `sync.Once`-guarded `styles.RegisterBuiltinThemes(fs.Sub(embed, "assets"))` called at the top of `applyTurfTheme` before any ref resolves) — five **terrain themes** built on the **astroturf pun** (the same astroturf imagined in different terrains): `meadow` (real turf), `stadium` (football-field astroturf), `sonora` (Arizona xeriscape), `lunar` (astroturf on the moon), `surf` (turf underwater). `stadium` is the default. Each is authored as near-complete partial YAML merged onto cagent's stock `DefaultTheme`, mapping the terrain's natural objects onto the palette — deliberately onto the `chroma.*` HCL syntax colors and the create/destroy/change status colors turf's renderers use, which **keep their semantics** (create ≈ green `success`, destroy ≈ red `error`, change ≈ amber `warning`) and are only terrain-tinted, so plans stay legible. Adding a theme is drop-in: the `//go:embed` glob picks up any new `assets/themes/*.yaml`; keep the `turfTerrainThemes` list in `theme_test.go` in lock-step. They resolve via `LoadTheme`, appear in the theme picker (`/settings` → Appearance → Theme), and persist exactly like cagent's bundled built-ins. The fork's bundled `calm-roots` remains selectable.

**Model selection:** `--model` accepts three forms — a named model from `turf.yaml` (see below), an inline `provider/model` (e.g. `anthropic/claude-sonnet-5`), or `auto`. Resolution lives in `models.go`: `pickModel` chooses the reference by precedence **`--model` / `TURF_MODEL` > `turf.yaml` `model:` > built-in default `auto`** (the flag defaults to the `TURF_MODEL` env value, so a non-empty `flagModel` already encodes "CLI > env"; leaving the cobra default empty lets `pickModel` tell "user set it" from "unset" so a config default isn't clobbered by a flag default). `resolveModel`/`selectModelConfig` then turn that reference into a concrete `latest.ModelConfig` and construct the provider via cagent's full factory — `providers.NewDefaultRegistry().New(...)`, the same registry cagent's own teamloader uses — dispatching to every provider cagent supports (cloud: openai/anthropic/google/amazon-bedrock; local: `dmr`/Docker Model Runner; plus OpenAI-compatible aliases ollama/mistral/groq/deepseek/xai/azure/…), filling in each provider's default base URL, token env var, and API type, and expanding `${env.*}` refs. turf adds **no selection logic of its own** — `auto` delegates to `config.AutoModelConfig` (first provider whose credentials are set, dmr as keyless final fallback) and `first_available` to `config.ResolveFirstAvailableModels`. An **unknown provider errors** here instead of silently falling through to OpenAI — surfacing a typo (`selectModelConfig` wraps the inline-parse failure as `invalid model …`). `--base-url` (env `TURF_MODEL_BASE_URL`) overrides `ModelConfig.BaseURL` for arbitrary OpenAI-compatible servers (vLLM, LM Studio, gateways); DMR/Ollama resolve their own local endpoints and need none. On failure, `modelProviderError()` wraps the cause with actionable launch guidance that features the keyless local-model path and links Docker's providers overview — the "great error when turf can't launch" surface. **Local models need a `context_size`, and turf sets no default:** turf's first request is ~27k tokens (measured: the MCP server's own instructions ~30.7 KB + 39 tool schemas ~68.8 KB + the persona, all of it in every request), which is a floor compaction cannot shrink, while Docker Model Runner runs with a far smaller default window and rejects that first message with `exceeds the available context size`. The knob is cagent's `provider_opts.context_size` — POSTed to DMR's `/engines/_configure`, used to clamp `max_tokens` in the OpenAI client, and authoritative over models.dev in `resolveContextLimit` (so it also drives compaction and the TUI usage bar). cagent exposes it as a **manifest key only** (no flag, no env var, explicitly no default) and turf follows suit rather than guessing a value on the user's behalf — the memory cost is real, since the engine reserves cache for the whole window up front. Consequence for docs and guidance strings: a local model must be a **named `turf.yaml` entry** carrying `provider_opts.context_size` (65536 is what turf's docs standardize on); an inline `--model dmr/ai/qwen3` cannot carry per-model options and is therefore *not* a working recipe — `README.md` (Local models + two Troubleshooting entries), `modelProviderError`, and the `--model` flag help all say so. A `first_available` candidate may name another entry in `models:` (`config.resolveCandidate`), which is what lets the keyless-fallback idiom reference the configured local model instead of a bare ref. Ollama has the same failure with a different knob turf can't reach (`OLLAMA_CONTEXT_LENGTH` / Modelfile `num_ctx`). Wiring the full registry pulls the bedrock factory's AWS SDK deps into `go.mod` (indirect). **One provider registry** is created per run in `createAgentRuntime` and shared between the agent's model (`agent.WithModel`) and the `/model` switcher, so runtime switching instantiates providers identically. `newModelProvider` remains as a thin `resolveModel` wrapper (empty `turfConfig`) for call sites/tests that only pass an inline ref.

**Model configuration (`turf.yaml`) — the overlay foundation:** turf owns a config file (`config.go`) that is a **turf-owned overlay, not a cagent agent manifest** — turf keeps its agent identity (persona, the turf MCP toolset + its `turf_` prefix, the permission gates, `WithSequentialToolCalls`, the headless `user_prompt` swap, `RedactSecrets(false)`, the filesystem allow-list) in code and exposes only the sections it chooses. `loadTurfConfig(cwd)` reads and **merges** two files in increasing precedence, mirroring `loadTurfSkills`: `<TURF_HOME>/turf.yaml` (global) then `<cwd>/.turf/turf.yaml` (project — under the same `.turf/` dir that holds `skills/`; no walk up the tree). Merge is per-key on the `models:`/`providers:` maps (project entry replaces a same-named global entry); scalars (`model:`, `models_gateway:`) override when set. The `turfConfig` struct is a small turf wrapper whose `models:`/`providers:` **values reuse cagent's public `latest.ModelConfig`/`latest.ProviderConfig` types**, so the YAML is byte-for-byte what Docker's docs document — credential-based `first_available:` lists, named models, and tuning fields (`temperature`, `max_tokens`, `base_url`, `token_key`, …). It is parsed with `goccy/go-yaml`, which **honors the `json` tags** those types carry (verified — `first_available`/`max_tokens` unmarshal despite having no `yaml` tag). A named `first_available` model is resolved by building a **synthetic single-agent `latest.Config`** whose only agent references the selected model, so `ResolveFirstAvailableModels` (which only visits models reachable from an agent) is scoped to that one model — an unrelated, currently-unsatisfiable `first_available` entry elsewhere in the file does not fail the run. The **default is `auto`** (a behavior change from the old fixed `google/gemini-pro-latest`): zero-config "first available", so turf runs with whatever key is present. `first_available` is **config-file-only**; `--model` takes a named model, an inline ref, or `auto` (comma stays reserved for cagent's alloy multi-model syntax). Theme still persists separately in cagent's own `<TURF_HOME>/config.yaml` (`userconfig`, written by the `/settings` theme picker) — that schema is a closed struct with no overflow map and no interface seam, so it can't carry `first_available`/named models without a fork; the turf-owned `turf.yaml` sidesteps that and coexists with it.

**The `/model` picker:** `createAgentRuntime` wires `runtime.WithModelSwitcherConfig(buildModelSwitcherConfig(...))`, which flips `SupportsModelSwitching()` true so the **full TUI** `/model` command works (without it, `/model` reports "No models available"). The picker lists `turf.yaml`'s named models (best-effort-resolved for display) plus locally-pulled DMR models and the models.dev catalog filtered by available credentials — useful even with no configured models. `ModelsStore` is left nil (the runtime builds its own lazy models.dev store on first open). Switching is **session-scoped** — cagent's `SetCurrentAgentModel` writes an in-memory runtime override and persists it to the *session*, never to disk — so `turf.yaml` remains the persistent default; there is no write-back. The **lean TUI** has its own small command set (`/new`, `/compact`, `/model`, `/effort`, `/clear`, `/help`, `/exit`), `/model` among them; it does not dispatch the server's MCP prompts (`/guide`, `/up`, …), which reach the model as plain text there.

**Co-branding (`turf.yaml` `branding:`, `branding.go` + `config.go`):** lets a distributor (a TACO vendor) re-skin and re-voice turf without forking it — four keys, all **display or prompt surface only**: `theme`, `banner`, `welcome_message`, `additional_instructions`. It rides the existing `loadTurfConfig` global+project merge, but merges **per field** (`mergeBranding`) rather than wholesale, so a project file can override just the theme and inherit the rest of a global brand. **There is deliberately no `name` key**: turf keeps its own name on every surface that identifies it — the binary, `tui.WithAppName`/`appNameWithBranch`, the headless `cli.Config.AppName`, and the `agent.New` name that renders as the badge above each reply (`turfAgentName`, a const kept in lock-step with that call because it also keys the model-switcher's per-agent default and scopes `first_available`). So a co-branded turf still announces itself as turf, and `appName` stays singular: it is also the name the MCP toolset is registered under (`agent.go`), i.e. the source of the `turf_` prefix that the renderers, the `/tools` grouping, and the static `preApprovedTurfTools` allow-list all key on. `TestBrandingLeavesNamesAlone` pins the whole omission. (A rename was built and then deliberately reverted — it worked, since cagent injects an agent name into the prompt only via the *multi-agent handoff preamble* in `session.go` and turf is single-agent, so the name is pure display; it was dropped as a product call, not a technical one.) `additional_instructions` is appended *after* `workflowInstructions` under a `## Additional instructions` header — cagent contributes a single `Instruction()` system message, so concatenation is the mechanism, and appending last keeps turf's base workflow contract stated first. It is prompt content and can therefore steer the agent, which is acceptable because `turf.yaml` is user-owned config at CLI-flag trust level and nothing *structural* moves (the team-level allow-list, the `turf_` enumeration, and the filesystem `*os.Root` sandbox are all code). `welcome_message` replaces the text but not the *decision* to show one — only callers that already pass a welcome (chat, not up/destroy) get it. `theme` is a registered **ref, not a path** (`styles.LoadTheme` rejects `/`, `\`, `..`), so a distributor ships its YAML into `<TURF_HOME>/themes/` and names it — which also makes it appear in the theme picker; consequence: a *project* `turf.yaml` naming a theme still needs that theme installed globally. `banner` **is** a path, resolved **absolute at read time** (`resolveBrandingPaths`) against the declaring file's dir — load-bearing twice over: before the merge, so a global banner keeps resolving against `<TURF_HOME>` when the project file wins on other keys; and absolute, because the file is read much later (at TUI construction) and `turfHome()` can be relative (a relative `$TURF_HOME`, or the `.turf` fallback) while turf chdirs for `--chdir`/`--worktree` — all of which complete before the config loads. Everything degrades rather than fails: an unreadable/empty banner or an unloadable theme warns and falls back to turf's own. The overlay is **published once** by `createAgentRuntime` (`setBranding`, right after `loadTurfConfig`) into a package-level var read through accessors, because the brand surfaces sit in layers turf doesn't otherwise thread config through — the process-global theme engine and the TUI constructors — and every run command calls `createAgentRuntime` before `runTUI`. Worked examples live in the sibling `turf-examples` repo under `integrations/`.

**External MCP servers (`turf.yaml` `mcps:`, wired):** each entry names one server, stdio (`command`/`args`/`env`) or remote (`url`, `transport`, `headers`), merged per key like `models:`. `createAgentRuntime` starts each as an MCP toolset under its own name, so cagent prefixes its tools `<name>_` (disjoint from `turf_*`), and closes them in the run's cleanup. `${VAR}`/`${env.VAR}` in `env`/`url`/`headers` expand with the same provider as `models:`; a stdio server also gets the ambient environment, which wins on a key collision (`mcpStdioEnv`). Their tools are **not** pre-approved — they prompt (`preApprovedTools` names only turf's own and the trusted builtins). The co-branding example in `turf-examples/integrations/scalr/chat` wires Scalr's and OPA's servers this way.

**Future overlay sections (`turf.yaml`, not yet wired):** the same loader/merge machinery is the drop-in point for custom toolsets (`toolsets:`, instantiated via `teamloader.ToolsetRegistry.CreateTool` and appended to turf's built-in toolset slice) and inline/remote skills (`inline:` and `sources: [<url>]`, via cagent's `skills.Load`/remote cache). turf's directory-based `local` skill discovery (`turfskills.go`, `<TURF_HOME>/skills` + `<cwd>/.turf/skills`) stays authoritative for local skills — the manifest `local` token means the ecosystem dirs (`~/.claude`, `~/.codex`, `~/.agents`) that turf deliberately avoids, and `sources` can't name an arbitrary dir. Any such section must enforce turf's guardrails (e.g. never relax the mutation-approval gate), which is why it's an overlay rather than a raw manifest run through teamloader.

**Memory:** Each session stores agent memory in a SQLite database (`.turf/memory.db` in the working directory by default). Disable with `--no-memory`.

**Session persistence (conversation history, distinct from Memory):** turf persists the *conversation itself* to a SQLite **session store** (`.turf/sessions.db` in the working dir by default; `--session-db`, env `TURF_SESSION_DB`), **on by default**, disabled by `--no-session` — the pair deliberately mirrors `--memory-path`/`--no-memory`, and the per-project location is chosen so both dbs live with the project. Both default under the turf-owned **`.turf/`** dir (`.turf/sessions.db`, `.turf/memory.db`) — the same dir that already holds project skills (`.turf/skills/`) — which keeps the project root clean and lets one turf-owned rule (`.turf/*` except `!.turf/skills/`) ignore all of turf's machine-local state at once; `.terraform/` was rejected as a home because it is disposable/OTF-owned and a routine `tofu init`/clean would wipe durable history. This is a different axis from Memory: Memory is the agent's advisory *knowledge* (facts it chooses to store via the memory tool); the session store is the raw transcript. **Session anchoring under `--worktree`:** the session store is the one thing that does *not* follow cwd into a throwaway worktree. The mental model is `--chdir` → **anchor** → worktree: `--chdir` runs first (in `PersistentPreRunE`) and defines the anchor (the launch dir); the session store lives at the anchor; the worktree is derived from it. So `.turf/sessions.db` is pinned to the real project's launch dir, while memory (`.turf/memory.db`), the recorded session `WorkingDir`, and the inherited `turf-mcp-server` cwd all follow cwd *into* the worktree — a unified session history across a project's throwaway worktrees, with the transcript surviving a worktree that is later removed. Mechanically, `setupRunWorktree` (`worktree.go`) captures the anchor (the pre-worktree cwd) and returns it as a second value; the run commands thread it to `createAgentRuntime` as `agentOpts.sessionDBDir`, which resolves the default session path to `<anchor>/.turf/sessions.db` (an explicit `--session-db` still wins; with no worktree the anchor is `""` and the store falls back to cwd, byte-identical to before). Note the anchor is the *invocation dir*, not the git repo root — launching from a subdirectory anchors history there, not at the repo top. turf's generated `.gitignore` (the turf-mcp-server `init` scaffold, `gitignoreStub`) ignores everything under `.turf/` except the committed `.turf/skills/` (`.turf/*` + `!.turf/skills/`) so none of turf's machine-local state is committed — the dbs, their SQLite `-wal`/`-shm` sidecars, and the persistent `memory.lock` advisory lock (which cagent's memory file-lock leaves on disk after unlock). The mechanism is almost entirely cagent's: `createAgentRuntime` (`agent.go`) opens the store via `session.NewSQLiteSessionStore`, wires it with `runtime.WithSessionStore`, and closes it in the returned cleanup (the runtime never closes an embedder-owned store); cagent then **auto-registers a `PersistenceObserver`** that writes messages/summaries/errors lazily (empty sessions leave no row). `createAgentRuntime` returns the store as a new second value so callers can resolve a resume ref *before* the session is built. **Resume:** `resolveTurfSession` (`session.go`) takes the `--session`/`--continue` ref (via `resumeRef`, which folds `--continue`→`-1` and rejects a ref under `--no-session`), resolves it with `session.ResolveSessionID` (concrete ID or relative offset like `-1` = most recent) + `store.GetSession`, and **re-applies turf's `applyTurfSessionPolicy` on the loaded session**. That policy (extracted from `newSession`) sets the session-level flags tools-approved + `HideToolResults(false)`, matching what cagent's own resume path already re-applies — so the resumed session's display/approval flags reflect the current run. Note **tool pre-approval is no longer a session-level concern**: it is installed once at the **team level** (see the tool-pre-approval note below), which is a property of the runtime rather than of any single session, so a resumed session inherits it automatically without a per-session re-stamp. An explicit, not-yet-existing ID creates a session bound to that ID (via `WithID`), so a script driving `exec` can own the ID across turns. Resume covers **`chat` + `exec`** only; `up`/`destroy` still persist (and appear in the browser) but stay one-shot. `newSession` also stamps `session.WithWorkingDir(cwd)` — cagent leaves that field empty unless the embedder sets it, and the browser groups sessions by it ("This workspace" vs elsewhere), so without it turf's sessions never grouped under the dir they were created in. The **full TUI's `/sessions` browser lights up for free** once the store is wired (`app.SessionStore()` → `handleOpenSessionBrowser`); the **lean TUI has no browser**, so lean resume is flag-only. **No tabs (single-session, working-dir oriented like Terraform) + browser-load fork patch:** turf runs single-session — it passes `spawner=nil` to `tui.New`, so it never surfaces tabs. Several `pkg/tui/tui.go` fork patches make that coherent, all keyed off a new `m.tabsEnabled()` helper (`supervisor.Spawner() != nil`): (1) every tab affordance is suppressed when there is no spawner — the "+ new tab" status-bar button (both `SetShowNewTab` sites), the `Ctrl+t/w/p/n` keybindings and their `AllBindings`/help entries, and the `NewSessionMsg` (`/new`) and `ForkSessionMsg` (`/fork`) handlers are no-ops — so nothing advertises a capability that isn't there. The fork **also auto-drops the tab-only commands (`/new`, `/fork`) from the command palette, parser, and completion** via `disableTabCommands()`, called at the end of `tui.New`, which adds them (the `tabOnlySlashCommands` list) to the shared `WithDisabledCommands` map when `!tabsEnabled()` — so the single `commandCategories()` choke point (which feeds all three) strips them, and a single-session embedder needs no opt-out of its own (deliberately fork-side rather than a turf `tui.WithDisabledCommands` call). `/clear` is deliberately **not** suppressed — it resets the current view in place and needs no spawner. (2) `handleLoadSession` loads a browser-selected session **in-place** when there is no spawner (`m.supervisor.Spawner() == nil`), instead of spawning a new tab and failing with "session spawning is not available" (the pre-patch behavior: loading a session mid-conversation did nothing); the current session is already persisted, so replacing it loses nothing. **Workspace-scoped browser (single-dir-per-process):** turf is deliberately one-working-dir-per-process, so a session created in a *different* dir can't be re-rooted here (cagent's respawn path would need the nil `Spawner()`). Rather than list such sessions and then decline them — and rather than introduce a spawner, which would both re-enable tabs (tab affordances gate on `Spawner() != nil`) and imply a *second* `turf-mcp-server` subprocess + store per loaded dir (the server binds the process cwd) — the browser is simply **scoped to the current workspace** for single-session embedders. `handleOpenSessionBrowser` passes `dialog.WithWorkspaceScoped()` when `Spawner() == nil`, which locks the browser's workspace filter to this-dir-only and disables the `Ctrl+G` toggle, so cross-dir sessions never appear and there is no load path to guard against in the first place. In normal use this is a no-op (the per-dir store already holds only current-dir sessions); it bites under `--worktree`, where the anchor store accrues past runs whose `WorkingDir` is a (now-ephemeral) worktree — those stay hidden, which is also forward-compatible with resumable worktrees (resuming one makes it the current workspace, so its sessions surface). `replaceActiveSession`'s respawn is still guarded on a non-nil `Spawner()` as a backstop for the internal restore callers (they'd otherwise panic on the nil call). `WithWorkspaceScoped` is a small variadic fork option so the 17 existing browser-dialog test callers stay unchanged. A second fork patch (`pkg/tui/dialog/session_browser.go`) fixes an empty `/sessions` browser: cagent hid every session with an empty `Title`. A turf session can legitimately be untitled — a chat-only session with no infra tool gets no deterministic title (see **Session titling** below) — so keying visibility on the title dropped real sessions and the browser looked empty even though `--continue` and `GetSessionSummaries` worked. The patch keys the "non-empty" filter on `NumMessages > 0` instead of `Title != ""`, so real-but-untitled sessions show (rendered as "Untitled"). Pre-approval survives browser load (and `/clear`, `/new`, `/fork`) because it lives at the **team level**, not on the session — so it does not depend on any persisted session column. `mcptoolset_test.go`-style drift is guarded by `session_test.go`.

**Session titling (`sessiontitle.go`):** the **`sessionTitleCurator`** — a `runtime.EventObserver` registered via `runtime.WithEventObserver` in `createAgentRuntime` — owns titling **end-to-end**, composing titles **deterministically** (no LLM). turf does **not** wire cagent's built-in LLM titler (`app.WithTitleGenerator` is not passed in `tui.go`), and an earlier turf LLM-summarizer was removed too: cagent's one-shot forces `WithNoThinking()` + `max_tokens=20`, which **400s on turf's default model** (`google/gemini-pro-latest` — Gemini 2.5 Pro rejects `thinkingBudget=0`), and even a thinking-tolerant LLM call **mis-stated the resource counts** (it would invent "4 resources" / lift "force replace" from the trigger prompt). So titles are now built from what turf *actually did*, in the **`terraform plan` glyph idiom**: `<alias> · init` after `init`, then `<alias> · plan +A ~C -D`, `<alias> · applied +A ~C -D`, `<alias> · destroyed -D`. The counts are the server's own plan summary on an `up`/`destroy`/`apply` result (`plan.add/change/destroy`), parsed by the **same renderer view** the timeline line reads (`convergenceView`; `initView` and `workspaceOpenView` for the label) — so a title and the line beside it always agree. Following the terraform convention, a **replace** counts as **one add + one destroy** (`+1 ~0 -1`), not a change — exactly how the server counts it; `~` is reserved for genuine in-place updates. `isDestroy()` (pure-delete plan) picks the teardown wording; the leading label comes from **`sessionLabel`**, a four-rung ladder answering "which piece of infrastructure is this session about?" — **`workspace_alias`** (this session's handle, set exactly when several workspaces are open, and the token the user types in every later call; also the only one the server constrains, to `^[a-zA-Z0-9][a-zA-Z0-9_-]*$`) > **`config_alias`** (the configuration's own handle, minted by `init`) > **`workspace_name` but only when it is not the literal `"default"`** > the config-path base, then the cwd base (for a `"."` path). The `"default"` exclusion is the load-bearing rung and was a **real bug**: the server always sends the workspace name (no `omitempty`, defaulting to `"default"` from `.terraform/environment`), so the old `configAlias`, which preferred it outright, short-circuited on rung one in *every* session — its path fallbacks were dead code and **every session titled `default · init` / `default · plan +2 ~0 -0`**. The tests missed it because their init fixtures omitted the `workspace` key entirely, a payload the live server never sends; they now carry it, and six of them fail against the old precedence. The **alias-first** ordering is the same rule the timeline uses (`workspaceName` in `renderers.go`, now shared by `open` and `status`, matching `close` and the universal `errorTarget` fallback): the two fields differ precisely when an alias was set, and that is exactly when the name is *least* informative — the server steers callers toward `vars` over workspace names, so its own e2e fixtures pair a meaningful alias with `workspace_name: "default"`. The `"default"` skip is **title-only**: a timeline line reports one specific call, so `open` on the default workspace should say `default`, while a session-wide label must not name every session identically. The digest field is `label`, not `alias` — two of the four candidates are literally named *alias* on the wire and they are not the same thing. The **digest evolves** across `ingest` calls: `init` sets the label (and `open` sets it only if `init` did not — the reopen/resume path, which is also the one place a `workspace_alias` exists to prefer); an `up`/`destroy`/`apply` result of a **deploy or destroy** convergence (a refresh, import or invoke is upkeep and does not retitle) paused at `awaiting_approval` records that round's counts under `(convergence_id, round)` and sets `stagePlan` with them — every round is its own approval point, so the title shows the round now awaiting approval — and a `converged` result flips to `stageApplied` with the counts **summed over the convergence's recorded rounds** (fixture `core`: `plan +4` → `plan +2` → `applied +6 ~0 -0`; a round re-vended after a restart is keyed, so counted once). When a converged result carries a round the curator never saw planned — an auto-approved run (`turf up --yes` converges in one call) or a convergence followed again after a restart — the split is unknown: a destroy titles `destroyed -N` from the rounds' `applied` (a destroy applies only deletes), a deploy `applied N change(s)` rather than claiming none. A new `convergence_id` starts the sum over; any other ending (failed, stalled, cancelled — which arrive as MCP errors, already skipped by `OnEvent`) leaves the title on the last plan, which is what was still pending. **Synchronous + cheap:** `OnEvent` parses, updates the digest under `mu`, recomputes `title()`, and writes only when it differs from `sess.Title` — no LLM means no goroutine/`seq`/stale-drop machinery. It acts only on the **root session** (pinned at the first `OnRunStart`), ignoring delegated sub-session tool activity. A **chat-only session** (no turf tool → no deterministic signal) stays *Untitled* by design (the browser's `NumMessages > 0` filter renders it fine). **Persistence + live refresh (one `setTitle` sink):** always `store.UpdateSessionTitle` (durable — `/sessions` browser, resume, headless `up`/`destroy`) plus, when the interactive TUI installs an **emitter** (`runTUI`/`runLeanTUI` set it to `go a.UpdateSessionTitle(...)` after the app is built), the `SessionTitleEvent` the sidebar/window title read (the store write alone doesn't live-refresh). `createAgentRuntime` returns the curator so the TUI can wire that emitter; headless callers pass `_`. Because `app.WithTitleGenerator` is unwired, `/title` *regenerate* (no-arg) is inert; `/title <text>` (and the sidebar edit) manual-set still works — and **wins**. Ownership is **stateless** (no flag/baseline): the curator overwrites only a title it could have produced itself — empty or one matching `isAutoTitle` (a package regex covering every `title()` shape *including* the `· init` pre-plan title, so there is no bare-label special case; kept in lock-step with `title()` by the `TestAutoTitlePattern` invariant) — and never downgrades an existing milestone title back to `· init` (guarding the `init`-on-resume case, the one remaining stage check). Anything else is treated as human and left alone, which also means a human title **survives resume** (a prior-process human title doesn't match the auto pattern, so it's preserved; a prior auto title does, so new milestones still update it). The tracked tools are `titleCuratorTools`, tied to the live server tool set by a drift guard in `sessiontitle_test.go` (mirrors `permissions_test.go`); digest/format/gating are unit-tested against exact title strings, and `session_test.go` guards that a curator title survives resume.

**Telemetry (opt-out via `--no-telemetry`):** cagent ships anonymous usage telemetry **on by default** (env `TELEMETRY_ENABLED`, default true; events POST to `api.docker.com/events/v1/track` with a hardcoded key — session start/end, tool calls, token usage/cost, errors, plus a persistent install UUID, OS, version, language; no prompts/responses/file contents). turf keeps that default but exposes a first-class opt-out: `--no-telemetry` (env `TURF_NO_TELEMETRY`), mirroring `--no-memory`. It is implemented **env-var only** — `PersistentPreRunE` (in `root.go`) does an early `os.Setenv("TELEMETRY_ENABLED", "false")` *before* any subcommand builds the runtime or launches the subprocess, so it covers `chat`/`up`/`destroy` uniformly and propagates to `turf-mcp-server` via the `os.Environ()` handoff in `agent.go`. It only ever force-*disables*: when the flag is unset turf never writes the var, so an explicit user `TELEMETRY_ENABLED=false` is still honored. Note the client is attached to the runtime context only on the `cli.Run` exec path (cagent `pkg/cli/runner.go`), which is turf's non-interactive `runExec` (`up`/`destroy` without a TTY); the **interactive TUI** (`runTUI`/`runLeanTUI`) never attaches a client, so it emits no runtime telemetry regardless. Deliberately no structural `runtime.WithTelemetry(noop)` sink — the env var is the single lever (cagent reads it at telemetry-client init in `pkg/telemetry/utils.go`). cagent's own first-run telemetry banner and getting-started **tour** offer live in cagent's `cmd/root` and are never wired by turf's own `root.go`, so they don't appear.

**MCP server resolution:** `resolveMCPServer()` checks `--mcp-server` / `TURF_MCP_SERVER` first, then PATH for `turf-mcp-server`.

**Builtin toolset wiring (and what's left out):** `createAgentRuntime` wires four of cagent's builtin toolsets — `think`, `todo`, `memory`, `filesystem` — plus the MCP toolset and (conditionally) user skills. The selection is deliberate, not default: each wired tool fills a **distinct, non-competing slot**, and the authoritative "what to do" is always the **OpenTofu plan computed server-side by `turf-mcp-server`**, never an agent-side artifact. The mental model:
- `think` — what turf is *reasoning*. In-process, within-turn, zero side effects, asserts nothing (`ReadOnlyHint`). Pure pre-action scratchpad ("validate planned actions before executing") that *feeds* the plan. Safest possible tool; can't go stale, can't diverge from reality.
- `todo` — what turf is *doing right now*. In-memory, per-session step checklist. No persistence, no authority.
- `memory` — what turf *knows*. Persistent SQLite (`.turf/memory.db`); durable, **advisory** knowledge (preferences, decisions, conventions). Used silently to *inform* planning; orthogonal to the plan. A stale memory degrades gracefully (it's weighed against reality, never an instruction to act).
- `filesystem` — what turf *reads and authors on disk* (HCL, plan/state scaffolding). **Hard-sandboxed** to an allow-list of roots — the working dir, the scratch/`--tmp-dir` dir, and any `--allow-path` — via a symlink-hardened `*os.Root` (`allow` is assembled in `createAgentRuntime`; a symlink inside a root cannot escape it). This is turf's *only* agent-side write surface, and the sandbox is its blast-radius boundary; the `turf-mcp-server` subprocess does its own I/O outside it. All filesystem tools are pre-approved by name (see the tool-pre-approval note), so operations within the sandbox never prompt while nothing outside it is reachable.
- The **OpenTofu plan** (server-side) owns "what turf *will do*" — the single source of truth, reconciled against live infra state.

cagent's `tasks` toolset (`create_task`/`next_task`/dependency DAG, persistent `tasks.json`) is **deliberately NOT wired.** It is the one builtin that doesn't get its own slot: it stores persistent *actions* (not knowledge), and so competes with the OpenTofu plan as a second, unreconciled "what to do." For an infra tool that is dangerous — a stale persisted task ("create the bucket") is an instruction to mutate, and unlike OpenTofu state it never refreshes against reality; `next_task` also nudges toward autopilot, against turf's per-plan approval gate. `todo` already covers the in-flight checklist need. Revisit `tasks` only if turf grows an explicit multi-session *campaign / change-backlog* feature, and if so scope it to that (its own storage under `~/.turf`, persona wording that keeps it a notepad, not an autopilot) rather than enabling it for ordinary `up`/`destroy`.

**`--worktree` (wired narrowly for HCL authoring):** cagent's CLI ships two run-isolation wrappers — `--worktree` (a **git** boundary via `pkg/worktree`) and `--sandbox` (an **OS/process** boundary via `pkg/sandbox`). Both are host-process wrappers, not agent tools (the model can't invoke them); cagent sets up the isolation *before* launching the agent. Neither addresses turf's real blast radius — **OpenTofu mutating live cloud infrastructure via the `turf-mcp-server` subprocess** — which is instead governed at the OpenTofu **state/workspace + approval** layer (separate state, plan-then-approve, scoped credentials), the goal of the server's `/up`/`/destroy` flows. turf therefore leaves `--sandbox` unwired (a naive sandbox would more likely *break* turf — trapping the server subprocess + provider downloads and blocking the cloud-API calls that are its whole purpose — than secure it). **`--worktree` is the one narrow exception, now wired** (`worktree.go`): under the design where the server writes synthesized HCL directly into the working directory, drafting that generated config on a throwaway git branch is genuinely useful — the "HCL-authoring mode" this note used to reserve. It isolates only *config authoring*, not live infra. Mechanics: `--worktree[=name]` / `--worktree-base <ref>` are persistent flags (cover `chat`/`up`/`destroy`); `setupRunWorktree` creates the worktree from the current working dir (branched off `--chdir`) under `<TURF_HOME>/worktrees/<name>` via `worktree.WithRoot(turfHome())`, then **`os.Chdir`s into it before the runtime is built** — the single lever that redirects everything, because the `turf-mcp-server` subprocess inherits the CLI cwd (turf passes `cwd=""` to `NewToolsetCommand`), as do the filesystem tool's allow-list and the memory-db default. Teardown (`cleanupRunWorktree`) mirrors cagent: interactive-only, clean worktree auto-removed, dirty one prompts (default keep); the non-interactive `up`/`destroy` exec paths never remove it. The active branch is folded into the TUI status title (`versionWithBranch`/`appNameWithBranch` in `tui.go`). `--worktree-pr` is deliberately not exposed (PR continuation is a weak fit for infra authoring, though `pkg/worktree.CreatePR` supports it). Note `worktree.Create` requires an existing repo (`ErrNotGitRepository`); a future `git init`/commit helper (via the scoped shell tool) would be the complementary no-repo path.

**Secret handling (cagent `redact_secrets` deliberately OFF):** `createAgentRuntime` sets `agent.WithRedactSecrets(false)` explicitly. cagent only defaults this feature *on* through its YAML/teamloader path; turf builds the agent in code and bypasses that, so the field is already `false` — the explicit call records the decision rather than leaving it to an implicit default. cagent's `redact_secrets` is **pattern-based** (regex over known credential shapes — cloud keys, tokens, PATs) applied across tool args, pre-LLM messages, and tool output. For an infra tool that net is wrong in both directions: it misses arbitrary-shape secrets (a random DB password, a provider token matching no pattern — exactly what fills tfstate) and its effects on plan/state-heavy workflows are an unknown we don't want to absorb here. The intended, authoritative mechanism instead lives in the **`turf-mcp-server` via OpenTofu-native sensitivity** — values OTF marks `sensitive` (schema/variable/output marks, propagated through expressions; surfaced as the `after_sensitive`/`sensitive_values` parallel structures in plan/state JSON, or `cty` marks in-process). That is structural, not heuristic: it knows a leaf is secret regardless of shape, with near-zero false positives, and is the only place with the metadata to do it correctly. The design principle is mask-on-output / retain-for-execution (redact what reaches the model + transcript; keep the real value server-side for the provider). If that server-side handling ever lands and we still want a backstop for *unstructured* leaks (provider-authored error strings, model-fabricated echoes), revisit the flag then — but it is secondary to, not a substitute for, native sensitivity. Note also the `turf-mcp-server` `TF_LOG`/stderr sink is outside both mechanisms (provider debug logging can spill cleartext) — a separate hardening, not covered by either.

**Tool pre-approval (all turf tools run without a prompt; the agent confirms):** `createAgentRuntime` (in `agent.go`) installs a **team-level** permission checker — `team.WithPermissions(permissions.NewChecker(&latest.PermissionsConfig{Allow: preApprovedTools()}))` — where `preApprovedTools()` (in `permissions.go`) is the union of `preApprovedTurfTools` (**every** turf tool) and `preApprovedBuiltinTools()` — the cagent builtin toolsets turf trusts, kept as per-toolset lists each tied to its package's `ToolName*` constants by a `permissions_test.go` drift guard: **memory** (`preApprovedMemoryTools` — the advisory-knowledge store), **filesystem** (`preApprovedFilesystemTools`), and **todo** (`preApprovedTodoTools`). `Ask`/`Deny` are left empty. The permission layer therefore never prompts for a turf tool or a wired builtin. (`think` is not listed — it's a single, pure, read-only tool that already auto-approves via `ReadOnlyHint`; `todo`'s tools also carry `ReadOnlyHint` but are listed anyway, both for explicit trust and so a future hint change doesn't start prompting.) **Filesystem tools are pre-approved BY NAME, not by arg-scoped path patterns**, because the toolset is already hard-sandboxed to its allow-list roots — the working dir, the scratch/`--tmp-dir` dir, and any `--allow-path` — via a symlink-hardened `*os.Root` (built in `createAgentRuntime`). That sandbox, not the permission layer, is the real boundary: a file tool physically cannot touch anything outside the allowed roots, so pre-approving the writers (`write_file`/`edit_file`/`create_directory`/`remove_directory`, which lacked a `ReadOnlyHint`) only removes a prompt for work already confined to the sandbox, and **`--allow-path` widens the auto-approved area simply by widening the sandbox** — no separate permission wiring. (Arg-scoped patterns like `write_file:path=<cwd>/*` were rejected: the `paths` **array** args of `create_directory`/`remove_directory` stringify to `[...]` and never match a path glob, and models may pass relative paths a `<cwd>/*` prefix won't match — the capability sandbox is the correct, robust boundary.) **Team-level, not session-level, is load-bearing:** the dispatcher consults session-then-team permission checkers, and the team checker is a property of the runtime that outlives any single `session.Session` — so pre-approval survives session replacement (`/clear`, `/new`, `/fork`) and resume by construction, with no per-session re-stamp. (An earlier design stamped `session.WithPermissions` per session; that silently dropped the allow-list on `/clear`, since cagent's `App.NewSession()` preserves only tools-approved/hide-tool-results/working-dir — moving to the team level fixed that at the root.) A permission gate on `apply` would double-prompt right after the user approved a plan, friction on the tool that is the heart of the UX, so confirmation lives **in the agent**, guided by the persona (`workflowInstructions` in `agent.go`), in four shapes — **configuration edits**: files the agent *creates* in a new/empty configuration directory for a natural-language request need no separate confirmation (plan approval covers them), while edits to *pre-existing* `.tf`/`.tfvars` files — the user's own — seek one `user_prompt` yes/no summarizing the intended edits, then make that change-set without re-prompting; **plan approval** — every round of a convergence stops at its own approval point, and before each `turf_apply` carrying a `plan_digest` the agent follows **the server's own approval rule** (its instructions define low-risk: only creates and in-place updates, no replace, no delete of anything holding data, no IAM or network-exposure change): it approves a low-risk round itself and seeks a `user_prompt` for any other round, **always** for a destroy plan, and always for an import or invoke plan (the CLI's long-standing policy); a "yes" never carries over to a later round; **turf actions** — at `awaiting_actions` the agent performs each requested step, asks the user via `user_prompt` when a step's prompt says to, and answers every request in one `turf_apply` with `action_results`; **workspace deletion** — `turf_delete` gets its own targeted `user_prompt` with an irreversibility warning. `turf_cancel`, `turf_taint`, `turf_untaint` and `turf_refresh` need no confirmation (they apply nothing by themselves; a taint's replace appears in the next plan, which is approved like any other). **Who answers `user_prompt`** (`userPromptToolset`, `autoconfirm.go`): at an attended terminal, the person, through cagent's real dialog; under `--yes`/`--auto-approve`, a synthetic tool that answers every prompt yes (`User Prompt (auto-confirmed)`), attended or not; and in an **unattended run without `--yes`** (`up`/`destroy` over a pipe, `exec`, CI), a synthetic tool that answers every prompt **no** (`User Prompt (declined: unattended)`, with a reason naming `--yes`), so a destroy, a replace, an import or an invoke stops at its approval point and stays waiting in the engine instead of going ahead — **approval without a person takes `--yes`**. The agent's own approval of a low-risk round is the same in every mode (it asks no one). **Why this stays safe:** the turf-mcp-server still faithfully annotates each tool `destructiveHint`/`readOnlyHint`; the load-bearing property is that `preApprovedTurfTools` is an explicit, static, **`turf_`-prefixed** enumeration (cagent prefixes every server tool because the MCP toolset is registered under the `turf` name), *not* a blanket `turf_*` prefix match — so a new/unknown turf tool, or any third-party MCP tool the CLI may load in future, is absent from `Allow` and still prompts (fail-safe: worst case is over-prompting, never under-prompting), and the drift test fails CI until it is consciously classified. `agentConfirmTurfTools` (`{turf_apply, turf_delete}`) is a documentation + drift-guard subset naming the tools the persona confirms; it is deliberately **not** a mirror of `destructiveHint`. `permissions_test.go` ties it to the live server: every server tool must be pre-approved (completeness), and every *server-destructive* tool (`apply`, `cancel`, `delete`, `taint`, `untaint`) must be either in `agentConfirmTurfTools` or the explicit `destructiveNoConfirm` carve-out (`{turf_cancel, turf_taint, turf_untaint}` — none authorizes a new infrastructure change) — so a newly-destructive server tool forces a confirmation decision. cagent's approval precedence: yolo (`--auto-approve`) > session `Allow`/`Ask` > **team `Allow`/`Ask`** (where turf's pre-approval lives) > `ReadOnlyHint` > default `Ask` — the first checker to return a verdict wins (see `runtime.tool_dispatch` / `toolexec.Decide`), so `--auto-approve` still approves everything and read-only tools still auto-approve regardless of the list.

**Skills:** Two parallel mechanisms, kept non-colliding **by the `turf_` tool prefix**. (1) The turf MCP server vends `skill_deployment`/`skill_authoring`/`skill_guide` (the built-in infrastructure workflows) — but, because the MCP toolset is registered under the `turf` name (see `agent.go`), the model sees these as `turf_skill_deployment`, etc. (2) Users author their own skills as `SKILL.md` directories, surfaced via cagent's **unprefixed** `read_skill` / `read_skill_file` / `run_skill` tools (`turfskills.go`). **The prefix is load-bearing, not cosmetic:** the turf MCP server *also* exposes a `read_skill_file` (for its own skill attachments) that collides by name with cagent's user-skills `read_skill_file`. Two tools sharing a name make a provider reject the entire request — Gemini returns `400 "Duplicate function declaration found"`, which is fatal to every turn. The `turf_` prefix de-collides them (`turf_read_skill_file` vs `read_skill_file`); cagent strips the prefix before dispatching, so the server still sees the bare name. Each user skill is a directory: `<root>/skills/<name>/SKILL.md` with YAML frontmatter declaring at least `name` and `description`; supporting files (e.g. `references/*.md`) load on demand. Roots, low→high precedence: `<TURF_HOME>/skills` (global — org best practices, migration playbooks) then `<cwd>/.turf/skills` (project, versioned with the infra config). Skills with no frontmatter are skipped (that is why the *server's* skills, which lack frontmatter, only work through `turf_skill_*`, not `read_skill`). The toolset is wired only when at least one skill is found, so a user with none pays nothing.

**Theming:** turf ships **five built-in terrain themes** baked into the binary from `assets/themes/` (see `theme.go` / `registerTurfThemes`). They are a play on turf's own name — the **astroturf pun**: each theme imagines the *same astroturf laid down in a different terrain*, and its palette is drawn from the **natural objects of that place**. The conceit is not just decorative — it is mapped onto the parts of the TUI the eye actually tracks during a run: the **`chroma.*` HCL syntax colors** (keywords, attribute names, strings, numbers) and, crucially, the **create / destroy / change status colors** turf's renderers paint on every planned resource. Those status colors **keep their meaning** across all terrains (create ≈ green-family `success`, destroy ≈ red-family `error`, change ≈ amber-family `warning`) — the terrain only *tints* them, so a plan stays instantly legible while reading as its terrain. Each terrain also picks one natural object to carry "new growth" (create): grass in meadow, vivid turf in stadium, saguaro in sonora, an absurd astro-green on the moon in lunar, fresh seagrass in surf. The five: **`meadow`** (real turf in bloom — grass & loam canvas with wildflower buttercup/goldenrod yellows and thistle/lavender purples as the ink, green held back to the create), **`stadium`** (football-field astroturf — vivid turf, white chalk yard-lines, pigskin, penalty-flag red, first-down yellow; **the default**, set via the `defaultThemeRef` constant), **`sonora`** (Arizona xeriscape astroturf — adobe, sandstone, saguaro green, turquoise, sunset coral/gold), **`lunar`** (astroturf on the moon — grey regolith, black sky, Earthrise blue, and the lone astro-green create), and **`surf`** (turf underwater — seagrass on a deep teal-ocean canvas, sea-foam text, bioluminescent-cyan chrome, coral change, sea-urchin purple). The fork's bundled `calm-roots` and cagent's other built-ins remain selectable. Themes load and persist from turf's own config home — `~/.turf` (override with `TURF_HOME`), never `~/.cagent`. `--theme <name>` (env `TURF_THEME`) overrides the applied theme for a single run without changing the saved choice. To add a custom theme, drop a YAML at `~/.turf/themes/<name>.yaml` and select it in the full TUI under `/settings` → Appearance → Theme (there is no `/theme` command); edits hot-reload while the picker is open, and the choice survives restart. A partial YAML is merged onto the built-in default, so you only need to specify the colors you want to change.
