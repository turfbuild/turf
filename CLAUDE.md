# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```sh
make build      # compile to bin/turf (embeds git-derived version)
make test       # go test ./...
make fmt        # go fmt ./...
make vet        # go vet ./...
make tidy       # go mod tidy
```

Always build with `make build`, not `go build` — the Makefile injects the git-derived version via ldflags, which a bare `go build` omits.

Run a single test:
```sh
go test -run TestName ./...
```

## Architecture

`turf` is a thin CLI wrapper around the `turf-mcp-server` binary. It never imports turf server code — the only contract is MCP over stdio.

**Data flow:**
```
CLI (cobra commands) → createAgentRuntime() → cagent runtime → turf-mcp-server subprocess (MCP/stdio)
                                                             → OpenTofu providers (downloaded on demand)
```

**Key files:**
- `agent.go` — constructs the cagent runtime. Launches `turf-mcp-server` as a subprocess, wires up toolsets (MCP tools, filesystem, think, todo, memory, and — when present — user skills), and creates the cagent `agent`/`team`/`runtime`. Registers the MCP toolset under the **`turf` name** so cagent prefixes every server tool with **`turf_`** (e.g. `turf_skill_core`, `turf_read_skill_file`) — see the Skills note below for why. Contains `workflowInstructions`, a short persona that delegates workflow guidance to the MCP server's instructions and `turf_skill_*` tools, spells out the `turf_` prefix mapping (the server names its own tools bare), distinguishes those from user `read_skill` skills, and carries the **dispatch-ordering note** — batched tool calls execute sequentially in emission order, so the persona tells the model to order dependent calls correctly within a batch and to await a call's *result* before emitting a call whose arguments need it. Sequential execution comes from `runtime.WithSequentialToolCalls(true)` at `runtime.New`, a **cagent fork patch** (upstream ≥ v1.99.0 fans a model batch out in parallel, unconditionally — which raced turf's stateful, order-dependent planning tools into ordering errors; prompt-only discipline proved insufficient). The API-level `parallel_tool_calls=false` knob was rejected: only the OpenAI/DMR providers honor it (Gemini, turf's default, ignores it) and it costs one LLM round-trip per call, while dispatcher-side serialization keeps multi-call batching free. Drop the fork patch when upstream ships its planned tool-execution-strategy config.
- `mcptoolset.go` — `turfMCPToolset`, a thin decorator around the MCP toolset that improves how turf's tools present in the **`/tools` dialog**. `Tools()` files each tool under a functional sub-category (`turf · plan`, `turf · apply`, `turf · provider`, `turf · workspace`, `turf · state`, `turf · skills`) and gives it a friendly, verb-first **display** name (`turf_plan_approve` → "Approve Plan") via `Annotations.Title`, instead of one flat `turf` group of raw `turf_*` ids. Both come from `turfToolInfo`, the per-tool source of truth. Display-only — the model still calls `turf_*`; providers and permissions key on `Name`. The tool set (group + title) is kept in lock-step with the `permissions.go` lists by `mcptoolset_test.go`. `Kind()` masks the inner `MCP` classification so turf reads as a built-in capability, not an external MCP integration. The dialog itself (layout, sorting, **description truncation**) is owned by cagent and not customizable without forking, so these data-side fields (`Category`, `Annotations.Title`) are turf's only lever over it.
- `renderers.go` — custom TUI **timeline** renderers for every `turf_*` tool (one-liner that leads with the friendly `turfToolInfo` title, then target + colored status, with a Ctrl+O expand block: attribute diffs, ready-sets, evaluated outputs). Plugs into cagent's renderer registry through the **same entry point its own built-ins use** — `tui.WithToolRenderers(map[string]tool.Builder)` → `tool.Register`, with `tool.Builder` + `toolcommon.NewBase` + `toolcommon.Renderer` — keyed by exact tool name. The renderer map comes from `turfToolRenderers()`; the full TUI wires it via `tui.WithToolRenderers`, while the lean TUI (which never calls `tui.New`) registers the same map directly through the `registerTurfToolRenderers()` helper — both funnel through `tool.Register`, so lean and full render tools identically. Deliberately hand-writes each `Renderer` (not cagent's `SimpleRenderer`/`RenderTool` helpers, which model a one-arg/one-result line) and parses `msg.Content` JSON (not a typed `msg.ToolResult.Meta`, since turf results cross the MCP boundary as text). The leading title is resolved in `line()` from `turfToolInfo` rather than `DisplayName()`. Every tool has a renderer and every renderer leads with its title — both enforced by `renderers_test.go`. **Failed tool calls surface the framework's error text** rather than a bare title, and **lead with the request's target** so a failure is as scannable as a success: on `ToolStatusError`, cagent carries the error message in `msg.Content` (from its `ToolCallResult.Output`), which the shared `errorLine` renders as a red body (`styles.ToolErrorMessageStyle`) prefixed by the target (`addr(target) + " · "`) resolved via `errorTarget` — a per-tool `turfToolTargetArgs` lookup (mirroring each renderer's own running-branch target arg: `resource_addr`, `path`, `address`, provider `name`, …) with a universal `workspace_alias` fallback, read from `msg.ToolCall.Function.Arguments`. It follows the same Ctrl+O detail toggle as every other line — expanded, the full error wraps across as many lines as it needs; compact, it flattens to one line truncated with an ellipsis (`ansi.Truncate`, measured against the title+target prefix width so the target stays visible) to stay scannable (empty → `"failed"`). It reaches every renderer through the single uniform swallow point, the `!parseContent` fallback (now `fallbackLine`, which defers to `errorLine` on error else the bare title, so the completed-but-unparseable case is unchanged); the two renderers that don't parse JSON (`renderSkill`, `renderReadSkillFile`) call `errorLine` directly, and `TestEveryRendererReportsErrors` guards that none regress to a silent bare line. **Rendering OTF values (the general approach):** every JSON-decoded OpenTofu value funnels through one shared renderer, `renderValue` (+ `renderMap`/`renderList`), so nested maps/lists never fall through to a raw-JSON dump. It renders in the **`tofu plan` idiom** (which is HCL-*like*, not HCL — `=`-aligned `key = value`, `+`/`~`/`-` markers, `(known after apply)`, masking): non-empty maps and lists expand across indented, `=`-aligned lines; short all-scalar lists stay inline (`ports = [80, 443]`); structural punctuation (`{} [] = ,`) is muted while scalar leaves carry the color. Both value sites go through it — `kvLines` for plain views (resolved config, effect new-state, outputs, module/datasource/import/refresh state) and `attrDiff` for before→after diffs, which reads like `tofu plan`: top-level keys are `=`-aligned, and a **create/destroy propagates its `+`/`-` marker onto every nested line** (a marked block indents children +4 and closes its brace +2, reserving the marker column). A scalar `~` stays inline as `old → new`; a collection `~` is header-marked and shows the *new* value expanded — full per-line recursive sub-diffing (mixed `+`/`-`/`~` inside one block) is a deliberate non-goal. The `marker` is threaded through `renderValue`/`renderMap`/`renderList` (empty string = the unmarked `kvLines` view). `fmtVal` stays the **scalar-leaf** formatter only (quoting, numbers/bools, and the `__cty_unknown__`/`__cty_sensitive__` sentinel masks — reused at every nesting level so masking never leaks); `capLines` bounds any single block. This was a deliberate move away from a config-only HCL renderer (upstream `hclwrite` was evaluated and rejected — it fixes only resolved config and reads as a different aesthetic than the rest of the timeline). Because scalar output is byte-identical to the pre-nesting behavior, the existing per-tool tests stay green and `TestRenderValueNesting` guards the new expansion.
- `examples_test.go` — integration checks against the sibling `turf-examples` repo (resolved via `$TURF_EXAMPLES_DIR`, else `../turf-examples`; **skips** when absent, so CI without that checkout stays green). Asserts the turf example skill (`cli/.turf/skills`) loads via `loadTurfSkills`, and the cagent example `turf.yaml` still parses against the pinned docker-agent (including `skills: true`).
- `turfskills.go` — discovers user-authored `SKILL.md` skills from turf-owned locations **only** (`<TURF_HOME>/skills/<name>/SKILL.md` and `<cwd>/.turf/skills/<name>/SKILL.md`), never cagent's default `~/.claude`/`~/.codex`/`~/.agents` dirs. turf scans and parses these itself (cagent's `skills.Load("local")` is hardwired to the ecosystem dirs, and its frontmatter parser is unexported), building `skills.Skill` values for cagent's `skillstool.New`. Project skills override global ones on a name collision; the working-dir location is exactly `<cwd>/.turf/skills` (no walk up the tree). Populates `Skill.Files` (which cagent's own local loader leaves empty) so `read_skill_file` is exposed and supporting files are listed. Parses scalar frontmatter (`name`, `description` required; `context: fork` and `model` passed through).
- `prompts.go` — thin trigger prompts for `up` and `destroy` subcommands. The detailed step-by-step procedures live in the turf MCP server as the `/up` and `/destroy` prompts; this file just produces the initial user message that points the agent at them.
- `logging.go` — `setupLogging()` configures turf's **own** process-wide `slog` handler. Called first in `PersistentPreRunE` (before anything else), it routes all logs to a rotating file at `<TURF_HOME>/turf.debug.log` (path via `turfHome()`, since `paths.SetDataDir` isn't redirected until the TUI starts) and **never to stderr**, so cagent's runtime logging can't paint over the Bubbletea alternate screen — the fix for "model error dumps log spew over the TUI." The file always captures **Warn and above** (cagent reports some failures only through slog — e.g. its "Empty assistant turn" warning when a model returns an empty response and the turn ends with no output; discarding those made such failures undiagnosable). `--debug` (env `TURF_DEBUG`) lowers the file level to debug. If the file can't be opened, logs fall back to discard (and the error is surfaced only under `--debug`). This is turf's in-process logging only — **independent of the `--log-*` flags**, which pass through to the separate `turf-mcp-server` subprocess.
- `root.go` — cobra root command, all persistent flags (`--model`, `--mcp-server`, `--tmp-dir`, `--memory-path`, `--no-memory`, `--chdir`/`-C`, `--log-file`, `--log-level`, `--log-format`, `--theme`, `--debug`, `--lean`). `--lean` (env `TURF_LEAN`) opts into the lean TUI for the run (see `tui.go`/`runLeanTUI`); it is persistent so it covers `chat`, `up`, and `destroy` uniformly, and defaults off. `PersistentPreRunE` calls `setupLogging()` (see `logging.go`) first, then honors `--chdir`. `--chdir` (git/make-style short alias `-C`) `os.Chdir`s before any subcommand runs, in `PersistentPreRunE`. The three `--log-*` flags are pass-throughs to `turf-mcp-server`'s flags of the same name; when unset, the server falls back to the `TF_LOG_*` env-var family (inherited via `os.Environ()` in `createAgentRuntime`). `--theme` (env `TURF_THEME`) is read by `applyTurfTheme()` and overrides the saved `/theme` choice for the run. Also defines the `appName` constant (`"turf"`), used to brand the TUI status bar / window title via `tui.WithAppName` in `tui.go`.
- `chat.go`, `up.go`, `destroy.go` — the three subcommands. `up` and `destroy` detect TTY and route to `runTUI` or `runExec` accordingly.
- `tui.go` — `runTUI` (interactive Bubbletea UI via cagent's `tui` package) and `runExec` (non-interactive via `cli.Run`). `runTUI` calls `applyTurfTheme()` before building the TUI, because cagent's `tui.New` does not auto-apply a theme, and passes `tui.WithAppName(appName)` + `tui.WithVersion(Version)` so the status bar / window title read "turf <version>" instead of cagent's "docker agent" default. `runTUI` takes the first message as a plain `string` (not an `app.Opt`) so it can route it to either TUI. When `--lean` (see `root.go`) is set, `runTUI` delegates to **`runLeanTUI`**, which drives cagent's standalone lean TUI (`pkg/leantui`) instead: it renders to the normal terminal buffer (no alternate screen), drops the sidebar/tab bar/overlays, and **owns its own input loop** — so it builds no `tea.Program` and needs no wheel coalescer. Three wiring differences from the full path: (1) it must `a.Start(ctx)` the app itself (the full TUI's model does this in `Init`); (2) leantui reuses the **same global tool-renderer registry** but never calls `tui.New`/`tui.WithToolRenderers`, so `runLeanTUI` registers turf's renderers directly via `registerTurfToolRenderers()` (see `renderers.go`); (3) leantui reads the first message from `leantui.Config.FirstMessage` (a `*string`), **not** `app.WithFirstMessage`, so the prompt is threaded into the `Config`. The lean welcome banner is **hardcoded ASCII art, not derived from `AppName`** (unlike the full TUI's status-bar title): upstream leantui shows "docker agent" art, so turf brands it by passing its own `turfBanner` (a figlet "ANSI Shadow" render of "TURF", matching cagent's style) via `leantui.Config.Banner`. **That `Banner` field is a small turf addition to the cagent fork** (`pkg/leantui`, defaulting to the built-in art when unset) — the only fork change lean mode needs; everything else uses cagent's existing public API. `leantui.Config` has no `Version` field, so lean mode has no version in its status footer, and (passing `service.StaticSessionState{}`, whose `HideToolResults()` is always false) no `Ctrl+O` tool-result toggle — turf's renderers always emit their expanded detail block. Theme still applies (leantui reads the same `styles` package `applyTurfTheme()` configures).
- `theme.go` — theming. `turfHome()` resolves turf's config home (`$TURF_HOME`, else `~/.turf`); `applyTurfTheme()` redirects cagent's process-global theme engine (`paths.SetDataDir`/`SetConfigDir`) at that home and applies a theme. Theme precedence (low→high): `defaultThemeRef`, a real saved `/theme` choice, then the `--theme` flag. `defaultThemeRef` is the single constant for turf's brand default.

**Model selection:** `--model` takes a `provider/model` string (e.g. `anthropic/claude-sonnet-4-6`, or the keyless local `dmr/ai/qwen3`). `newModelProvider()` in `agent.go` routes it through cagent's full provider factory — `providers.NewDefaultRegistry().New(...)`, the same registry cagent's own teamloader uses — rather than a hand-rolled switch. That registry dispatches to every provider cagent supports (cloud: openai/anthropic/google/amazon-bedrock; local: `dmr`/Docker Model Runner; plus OpenAI-compatible aliases ollama/mistral/groq/deepseek/xai/azure/…), filling in each provider's default base URL, token env var, and API type, and expanding `${env.*}` refs. An **unknown provider errors** here instead of silently falling through to OpenAI — surfacing a typo rather than hiding it behind a confusing "OPENAI_API_KEY required". `--base-url` (env `TURF_MODEL_BASE_URL`) sets `ModelConfig.BaseURL` to override the endpoint for arbitrary OpenAI-compatible servers (vLLM, LM Studio, gateways); DMR/Ollama resolve their own local endpoints and need none. On failure, `modelProviderError()` wraps the cause with actionable launch guidance that features the keyless local-model path and links Docker's providers overview — the "great error when turf can't launch" surface. Wiring the full registry pulls the bedrock factory's AWS SDK deps into `go.mod` (indirect).

**Memory:** Each session stores agent memory in a SQLite database (`.turf-memory.db` in the working directory by default). Disable with `--no-memory`.

**MCP server resolution:** `resolveMCPServer()` checks `--mcp-server` / `TURF_MCP_SERVER` first, then PATH for `turf-mcp-server`.

**Builtin toolset wiring (and what's left out):** `createAgentRuntime` wires four of cagent's builtin toolsets — `think`, `todo`, `memory`, `filesystem` — plus the MCP toolset and (conditionally) user skills. The selection is deliberate, not default: each wired tool fills a **distinct, non-competing slot**, and the authoritative "what to do" is always the **OpenTofu plan computed server-side by `turf-mcp-server`**, never an agent-side artifact. The mental model:
- `think` — what turf is *reasoning*. In-process, within-turn, zero side effects, asserts nothing (`ReadOnlyHint`). Pure pre-action scratchpad ("validate planned actions before executing") that *feeds* the plan. Safest possible tool; can't go stale, can't diverge from reality.
- `todo` — what turf is *doing right now*. In-memory, per-session step checklist. No persistence, no authority.
- `memory` — what turf *knows*. Persistent SQLite (`.turf-memory.db`); durable, **advisory** knowledge (preferences, decisions, conventions). Used silently to *inform* planning; orthogonal to the plan. A stale memory degrades gracefully (it's weighed against reality, never an instruction to act).
- The **OpenTofu plan** (server-side) owns "what turf *will do*" — the single source of truth, reconciled against live infra state.

cagent's `tasks` toolset (`create_task`/`next_task`/dependency DAG, persistent `tasks.json`) is **deliberately NOT wired.** It is the one builtin that doesn't get its own slot: it stores persistent *actions* (not knowledge), and so competes with the OpenTofu plan as a second, unreconciled "what to do." For an infra tool that is dangerous — a stale persisted task ("create the bucket") is an instruction to mutate, and unlike OpenTofu state it never refreshes against reality; `next_task` also nudges toward autopilot, against turf's per-plan approval gate. `todo` already covers the in-flight checklist need. Revisit `tasks` only if turf grows an explicit multi-session *campaign / change-backlog* feature, and if so scope it to that (its own storage under `~/.turf`, persona wording that keeps it a notepad, not an autopilot) rather than enabling it for ordinary `up`/`destroy`.

**Isolation features left unwired (`--worktree`, `--sandbox`):** cagent's CLI ships two run-isolation wrappers that turf intentionally does **not** expose — both isolate the wrong layer for an infra tool. These are host-process wrappers, not agent tools (the model can't invoke them); cagent sets up the isolation *before* launching the agent and they are mutually exclusive with each other. `--worktree` (`pkg/worktree`) is a **git** boundary: it runs the agent in a throwaway `git worktree` on its own branch so file edits land off your checkout, but the agent keeps full host network, env, credentials, and cloud access — and cagent never commits or pushes (a clean worktree is auto-removed on exit; a dirty one prompts keep/discard, leaving you to `git commit`/`push`/merge by hand). `--sandbox` (`pkg/sandbox`) is an **OS/process** boundary: it runs the agent inside a Docker container (template `docker/sandbox-templates:docker-agent`) with only the workspace bind-mounted and network allowlisted. Neither addresses turf's actual blast radius, which is **OpenTofu mutating live cloud infrastructure via the `turf-mcp-server` subprocess**: a worktree changes nothing about that, and a naive sandbox would more likely *break* turf (trapping the server subprocess + provider downloads, and blocking the cloud-API calls that are turf's whole purpose) than secure it. The isolation turf actually wants lives at the OpenTofu **state/workspace + approval** layer (separate state, plan-then-approve, scoped credentials) — already the goal of the server's `/up` and `/destroy` flows. So these are correct omissions, not gaps; revisit `--worktree` only narrowly if turf grows an HCL-*authoring* mode where drafting generated config on a throwaway branch is useful.

**Secret handling (cagent `redact_secrets` deliberately OFF):** `createAgentRuntime` sets `agent.WithRedactSecrets(false)` explicitly. cagent only defaults this feature *on* through its YAML/teamloader path; turf builds the agent in code and bypasses that, so the field is already `false` — the explicit call records the decision rather than leaving it to an implicit default. cagent's `redact_secrets` is **pattern-based** (regex over known credential shapes — cloud keys, tokens, PATs) applied across tool args, pre-LLM messages, and tool output. For an infra tool that net is wrong in both directions: it misses arbitrary-shape secrets (a random DB password, a provider token matching no pattern — exactly what fills tfstate) and its effects on plan/state-heavy workflows are an unknown we don't want to absorb here. The intended, authoritative mechanism instead lives in the **`turf-mcp-server` via OpenTofu-native sensitivity** — values OTF marks `sensitive` (schema/variable/output marks, propagated through expressions; surfaced as the `after_sensitive`/`sensitive_values` parallel structures in plan/state JSON, or `cty` marks in-process). That is structural, not heuristic: it knows a leaf is secret regardless of shape, with near-zero false positives, and is the only place with the metadata to do it correctly. The design principle is mask-on-output / retain-for-execution (redact what reaches the model + transcript; keep the real value server-side for the provider). If that server-side handling ever lands and we still want a backstop for *unstructured* leaks (provider-authored error strings, model-fabricated echoes), revisit the flag then — but it is secondary to, not a substitute for, native sensitivity. Note also the `turf-mcp-server` `TF_LOG`/stderr sink is outside both mechanisms (provider debug logging can spill cleartext) — a separate hardening, not covered by either.

**Tool pre-approval (safe turf tools run without a prompt):** `newSession` (in `agent.go`) sets `session.WithPermissions(&session.PermissionsConfig{Allow: preApprovedTurfTools, Ask: alwaysConfirmTurfTools})` — the two curated lists live in `permissions.go`. The policy mirrors turf's real safety boundary, the plan-then-approve gate: everything upstream of it (reads, provider discovery, and building the in-memory **Draft** via the `*_plan`/`*_init` tools) has no effect on live infra or persisted state and is pre-approved so the agent doesn't stop for a human OK on every planning step. Only the mutation gate stays behind confirmation — `effect_apply`, `action_invoke`, `effect_cancel`, `workspace_delete`, and the two state-writing tools `resource_import`/`resource_refresh`. `plan_approve` — the Draft-sealing review gate — is **pre-approved**, not confirmed: it authorizes no live-infra change (`effect_apply` still does, behind confirmation) and is `destructiveHint=false`, and the model already captures the human OK upstream via the built-in `user_prompt` dialog (per the `/up`/`/destroy` persona), so a second prompt on `plan_approve` was a redundant double-confirmation. (Future: have `plan_approve` elicit via MCP directly, then move it back to always-confirm.) One deliberate exception runs the other way: `workspace_close` is server-annotated `destructiveHint=true` (it persists state) but is **pre-approved** anyway, because it authorizes nothing new — it just flushes state from already-approved effects and is the bookend of the pre-approved `workspace_open` (the server tells the agent to "always call it when done"). That exception is tracked explicitly in `permissions_test.go` (`destructiveButPreApproved`) so the drift guard still blocks every *other* destructive tool from being auto-approved. Names are the **`turf_`-prefixed** LLM-facing names (cagent prefixes every server tool because the MCP toolset is registered under the `turf` name). cagent's approval precedence is yolo (`--auto-approve`) > session `Allow`/`Ask` > `ReadOnlyHint` > default `Ask`: so `--auto-approve` still approves everything unchanged, the `Allow` list runs silently otherwise, and the `Ask` entries are belt-and-suspenders (`Ask`/ForceAsk also overrides `ReadOnlyHint`, so a gate tool can't be silently auto-approved even if the server later mis-annotates it read-only). Note cagent *already* auto-approves any tool the server marks `readOnlyHint=true` (turf's pure-read tools carry it, and it survives the `turfMCPToolset.Tools()` wrapper); the `Allow` list is what additionally clears the planning/staging tools, which are `destructiveHint=false` but **not** read-only (they mutate the Draft). The list is a deliberately **static** CLI-owned policy, not derived from server annotations — a new/unknown server tool is absent from `Allow` and therefore prompts (fail-safe: worst case is over-prompting, never under-prompting).

**Skills:** Two parallel mechanisms, kept non-colliding **by the `turf_` tool prefix**. (1) The turf MCP server vends `skill_core`/`skill_adhoc`/`skill_codified` (the built-in infrastructure workflows) — but, because the MCP toolset is registered under the `turf` name (see `agent.go`), the model sees these as `turf_skill_core`, etc. (2) Users author their own skills as `SKILL.md` directories, surfaced via cagent's **unprefixed** `read_skill` / `read_skill_file` / `run_skill` tools (`turfskills.go`). **The prefix is load-bearing, not cosmetic:** the turf MCP server *also* exposes a `read_skill_file` (slug-based, for its own skill attachments) that collides by name with cagent's user-skills `read_skill_file` (skill_name-based). Two tools sharing a name make a provider reject the entire request — Gemini returns `400 "Duplicate function declaration found"`, which is fatal to every turn. The `turf_` prefix de-collides them (`turf_read_skill_file` vs `read_skill_file`); cagent strips the prefix before dispatching, so the server still sees the bare name. Each user skill is a directory: `<root>/skills/<name>/SKILL.md` with YAML frontmatter declaring at least `name` and `description`; supporting files (e.g. `references/*.md`) load on demand. Roots, low→high precedence: `<TURF_HOME>/skills` (global — org best practices, migration playbooks) then `<cwd>/.turf/skills` (project, versioned with the infra config). Skills with no frontmatter are skipped (that is why the *server's* skills, which lack frontmatter, only work through `turf_skill_*`, not `read_skill`). The toolset is wired only when at least one skill is found, so a user with none pays nothing.

**Theming:** The TUI ships with a distinctive default theme (`calm-roots`, set via the `defaultThemeRef` constant in `theme.go`). Themes load and persist from turf's own config home — `~/.turf` (override with `TURF_HOME`), never `~/.cagent`. `--theme <name>` (env `TURF_THEME`) overrides the applied theme for a single run without changing the saved `/theme` choice. To add a custom theme, drop a YAML at `~/.turf/themes/<name>.yaml` and select it in the TUI with `/theme`; edits hot-reload while the picker is open, and the choice survives restart. A partial YAML is merged onto the built-in default, so you only need to specify the colors you want to change. A fully custom turf-branded theme baked into the binary is a tracked follow-up (see the TODO in `theme.go`).
